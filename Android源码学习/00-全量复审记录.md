## 2. 复审方法

每篇至少按下面六层检查：

1. **版本层**：结论是否属于 Android 11 r48，后续版本差异是否明确标出；
2. **导航层**：文件路径、类名、方法名和接口源是否真的存在；
3. **控制流层**：请求入口、状态变更、异步调度、完成回执和失败清理是否连得上；
4. **运行边界层**：代码运行在哪个进程、线程和锁内，是否跨 Binder、JNI、HAL 或内核；
5. **语义层**：常量、阈值、timeout 起点/取消点、返回值和持久化时机是否准确；
6. **教学层**：先给心智模型，再贴关键源码；明确“证明什么”和“不证明什么”；练习保持 macOS 只读。

对源码注释、Javadoc 和可执行代码不一致的地方，以本 tag 的可执行代码为准，同时把差异写入正文，避免读者以后再次掉进同一陷阱。

## 4. 这次修正了哪些典型问题

### 4.1 启动与组件时序

- 明确 r48 中 `PHASE_BOOT_COMPLETED` 先推进，随后才写 `sys.boot_completed=1`；二者又都不等于所有用户的 `BOOT_COMPLETED` Receiver 已执行完，更不能证明 Launcher 首帧已经显示。
- 修正 Activity 冷启动理解：AMS 发出 oneway `bindApplication()` 后不会同步等待 `Application.onCreate()`，ATMS 可以继续发送 launch transaction；App 主线程按入队顺序消费两类消息。
- 将 Provider 的 attach 后 10 秒 publish timeout、调用方进入等待后的 20 秒 ready timeout，以及已发布 Provider 业务调用无响应分成三条不同路径；前两条并不会自动走统一 ANR 链。
- 修正 Service execution 的 20/200 秒含义：它取决于这次执行登记的前台紧迫性，不等于 Service 已经是 foreground service；`startForegroundService()` 的 10 秒承诺又是另一套计时器。

### 4.2 Binder、进程与完成语义

- 全局统一 oneway 语义：调用返回只表示客户端不等业务 reply，不证明服务端已处理、硬件已完成或业务成功；顺序约束也不能外推成跨 Binder 对象、跨 Handler 或多客户端的全局顺序。
- 修正 `Parcel.appendFrom()` 的过度承诺：r48 会复制完整落入范围的 Binder/FD 对象，但不会替调用者验证任意协议切片边界。
- 修正 `FAILED_TRANSACTION` 到 `TransactionTooLargeException` 的映射条件：r48 JNI 只在远端异常且 data Parcel 大于 200 KiB 的启发式条件下映射；小 Parcel 常表现为 `DeadObjectException`。
- 明确 stable/unstable Provider 引用不是 Java/Binder 强弱引用；它们影响 OOM 依赖、宿主死亡后的客户端处置和缓存恢复策略。

### 4.3 图形、输入、音频与硬件接口

- 补清 Android 11 r48 的 BLAST 开关边界：DeviceConfig 默认并非让所有 App 窗口自动走 BLAST，还需满足 WMS 与窗口 flag 条件。
- 修正 UI/RenderThread 等待关系：UI 通常等待 RenderThread 的同步/准备阶段，不是等待 GPU、SurfaceFlinger、HWC 已经把像素显示到物理屏幕。
- 修正窗口输入信息传递：WMS 把 input info 写入 SurfaceControl transaction，SurfaceFlinger 按 Layer Z-order 汇总后再交给 InputFlinger/InputDispatcher；不是 WMS 直接把整张窗口表塞给 Dispatcher。
- 修正 AudioTrack 创建路线：客户端先向 AudioFlinger 请求 createTrack，AudioFlinger 服务端再经 AudioPolicy 查询 output 和路由。
- 相机、Sensor、GNSS、Radio、Supplicant、Keymaster、GateKeeper 等 HIDL 章节统一指向仓库中的 `.hal` 契约源；常见 `I*.h` 是构建生成头，不能当作本地源码入口。

### 4.4 网络、电源与系统策略

- 区分 Java 进程内 DNS AddressCache 与 DnsResolver 的 per-network cache，补清 NO_CACHE lookup/store 标志。
- 修正“所有 UID 网络策略都落成 eBPF”的笼统描述：Data Saver 与 owner firewall 在 r48 有不同的 iptables/eBPF 执行路径。
- 修正 Tethering 上游选择并非统一以 `VALIDATED` 为硬门槛；同时限定 r48 `BpfCoordinator` 重点覆盖 IPv6 邻居转发 offload、配额和统计，不能代表全部 IPv4 NAT 数据面。
- 修正 Ethernet 时序：client mode 接口 link-up 后可直接启动 IpClient，不必等新的 NetworkRequest；server mode 则转交 tethering。
- 补清 `ACQUIRE_CAUSES_WAKEUP` 与 PARTIAL_WAKE_LOCK：API 合同禁止组合，但 r48 某些校验路径未直接抛错；服务端仍只对 screen lock 应用 wake-up 语义，不能以“没报错”推断组合有效。

### 4.5 OTA、安全、崩溃与恢复

- 修正 APEX 的运行时 manifest、staged session、checkpoint retry、DE 数据准备、activation failure 与 revert 时序。
- 明确 Rollback 的 COMMITTED 内存状态和成功回调后的落盘不是同一瞬间，并分开普通 APK broadcast 与 staged session 的 enable 入口。
- 修正 DropBox 文件持久化描述：r48 的 `sync()` 发生在 close/压缩尾部完成之前，不能说最终全部字节已经被该次 fsync 覆盖。
- 修正 tombstone 完整性：tombstoned 完成后才 `linkat` 发布正式文件，BootReceiver 的主要缺口是启动扫描到 FileObserver 生效之间的窗口，不是通常会读到正式路径的半文件。
- 修正 LMKD 文档与实现差异：同仓库 README 对 `kill_timeout_ms` 的默认描述是 0，而 r48 执行代码默认是 100 ms，且仍可被产品属性覆盖。

### 4.6 广播、同步与 JobScheduler

- 修正 BroadcastDispatcher：Receiver timeout 分支在调用 `finishReceiverLocked()` 前重置 `receiverTime`，所以这次 timeout 通常不会再按完整超时时长触发慢 Receiver deferral。
- 修正 AppTimeLimit 查询：选择的是“剩余时间最少”的限制，不是“总额度最小”。
- 修正 QuotaController：短期 rate window、bucket session 合并和跨 bucket 计数缓存是不同账本；不能靠切换 bucket 绕过防刷限制。
- 修正 SyncManager 旧 Javadoc 陷阱：r48 已没有旧的 30 分钟 SyncManager timer；当前可见的是 JobServiceContext 的默认 10 分钟执行片和每 60 秒按 Adapter UID 总流量做的无进展检查。
- 修正 `restoreAllPeriodicSyncs()` 推断：r48 保留 parser/helper，但全树中 helper 只有定义、没有生产调用点，不能写成开机主链必然迁移；当前周期同步的权威调度仍在 JobScheduler persisted Jobs。

## 6. 复审后的阅读建议

不要试图一次记住所有类名。每章先回答四个固定问题：

1. 入口在哪个进程、哪个线程？
2. 哪一步跨 Binder/JNI/HAL/内核？
3. 哪个状态属于“请求已受理”，哪个状态才属于“业务已完成”？
4. 失败后谁清理、谁重试、证据写到哪里？

看到一个 timeout 时，再强制补三问：**从哪里开始计时、在哪里取消、到期后到底是返回失败、杀进程、ANR，还是仅调整调度资格？**
