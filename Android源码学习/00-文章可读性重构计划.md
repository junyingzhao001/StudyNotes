# Android 源码学习文章：可读性重构计划

> 建立时间：2026-09-03  
> 源码基线：Android 11 / API 30 / `android-11.0.0_r48`  
> 本文件只记录文章质量重构，不替代原有的章节学习进度。

## 先给结论

现有 01—586 章的主要问题不是“没有资料”，而是**资料太多、主线太弱**：不少文章保留了版本、线程、进程和失败边界，准确性意识较好；但固定数量的小标题、过长代码和“初稿/复读/修订”等写作过程，把“为什么值得学、它解决什么问题”埋住了。

本轮重构的目标不是简单缩短文章，而是让每章都能回答四个问题：

1. 现实中遇到什么现象时，需要这章知识？
2. Android 为什么这样设计？
3. 哪几行源码足以证明核心结论？
4. 读完后能自己完成什么验证？

## 新的单章标准

### 1. 开头先回答读者最关心的事

首屏必须出现：

- 一个真实、可识别的现象或故障；
- 一句话核心结论；
- 读完能获得什么排查或阅读能力；
- 本章明确不解决什么，避免范围失控。

不用“本文将介绍……”连续铺垫，也不先堆缩写。

### 2. 一章只保留一条主线

默认采用：

```text
问题 → 一句话结论 → 为什么这样设计 → 关键调用链
     → 精简源码证据 → 边界/翻车点 → 本地验证 → takeaway
```

每章只选一个贯穿场景。其他例子只有在能澄清边界时才保留，并降为一句对照，不再横向铺开五个相似例子。

### 3. 标题表达问题，而不是罗列名词

- 一般控制在 6—12 个二级标题；复杂章可适当增加，但不追求固定数量。
- 细节使用三级标题或表格，不把每个字段都提升成同级章节。
- 标题尽量回答“为什么、什么时候、怎样验证”，避免把十几个术语连成一个长标题。

### 4. 源码只承担“证明”职责

- 一个代码块通常保留 5—15 行。
- 只展示能证明调用方向、线程切换、状态提交、返回值或失败分支的代码。
- 省略部分必须用文字说明，不伪造连续源码。
- 每段代码后立即写清楚“这几行证明了什么”。
- 给出真实文件路径、类名和方法名；行号只作当前版本参考。

### 5. 图表按问题选择，不按篇数凑数

- 跨进程、跨线程和先后顺序：时序图。
- 分层、所有权和职责：架构图。
- 多个维度的区别：对比表。
- 一个短段落能说清楚时，不画图。

不再要求每篇固定三张图。

### 6. 先讲 Why，再讲 How

首次出现一个机制时，顺序是：

1. 不这样做会出现什么问题；
2. Android 选择了什么办法；
3. 源码怎样落实；
4. 这个办法付出了什么代价。

类比只用来建立第一层模型，随后必须回到真实类名、进程和线程，避免用类比代替技术事实。

### 7. 坦诚写边界，不虚构数据

结论分成三类：

| 类型 | 写法 |
|---|---|
| 源码可确定 | 明确引用当前版本的类、方法或配置 |
| 基于源码的推断 | 标注“由此可以推断”，说明推断链 |
| 需要设备验证 | 给出验证方法和预期观察，不冒充实测结果 |

没有真实测量时，不写“性能提升 80%”之类数字。macOS 只做静态阅读的章节，要明确哪些运行结果尚未实测。

### 8. 删除写作过程，保留修正后的知识

正文删除或改写：

- “生成后复读”；
- “初稿遗漏”；
- “本轮修订”；
- “二次审计后发现”；
- 纯占位的下一章预告。

若修正本身能帮助读者避坑，直接写成“容易误判的地方”，不叙述作者如何改稿。

### 9. 结尾必须能立刻行动

每章至少给一个可完成的练习，并包含：

- 从哪个文件或入口开始；
- 要沿哪几个符号追踪；
- 应记录什么；
- 预期能证明或排除什么；
- 检查题的答案或明确观察标准。

## 单章验收清单

完成一章后逐项检查：

- [ ] 前 20—30 行说明了问题、结论、价值和范围。
- [ ] 全文能用一句话说出唯一主问题。
- [ ] 叙事整体符合“问题→方案/机制→验证”。
- [ ] 先解释设计动机，再出现大段源码细节。
- [ ] 主要概念只由一个贯穿场景承载。
- [ ] 二级标题有清晰层级，不存在机械凑数。
- [ ] 代码只保留关键行，并紧跟解释。
- [ ] 图表确实比文字更清楚。
- [ ] 进程、线程、同步/异步和完成点没有混写。
- [ ] API、内部实现和 Android 版本边界已分别说明。
- [ ] 没有编造项目经历、踩坑故事或性能数据。
- [ ] 删除“初稿/复读/生成过程”等元叙事。
- [ ] 结尾有可执行验证和答案/预期观察。

## 改写顺序

先改“会影响后续理解方式”的基础章，再改严重超长章，最后顺序覆盖全部文章。

| 优先级 | 范围 | 原因 |
|---|---|---|
| P0 | 01、07—10、17—18、90—98 | Framework、Binder、线程和系统启动等基础模型一旦理解错，会污染后续阅读 |
| P1 | 13、19—20、62、100、128、131—136、157—168、214—217、220、236、250 | 信息量或代码量过大，需要重新确定唯一主问题 |
| P2 | 253—400、401—586 | 固定 120 节模板最集中，优先合并层级、删除过程文字 |
| P3 | 其余章节 | 按编号逐章重构并复核 |

文件名和编号保持不变，避免破坏 README 链接和既有阅读顺序。必要的扩展材料放在章末“进一步追踪”，不另造无编号碎片。
