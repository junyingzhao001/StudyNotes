# 19 · 错误模型：返回值、异常、optional 与 variant

[返回学习地图](../README.md) · [上一篇](18-算法迭代器与ranges.md) · [下一篇](20-流与格式化.md)

## 先说这篇讲什么

这篇讲不同失败应该怎样表达。目标不是只选异常或错误码，而是让调用者不会漏掉重要失败。

## 它有什么用

找不到数据、文件损坏、参数不合法和程序内部断言是不同问题。把它们混成 false 会丢掉原因，全部抛异常又会让普通分支难读。

## 要解决的问题

查询“可能没有结果”是正常情况，optional 很合适；配置文件格式损坏通常需要携带原因并停止当前操作。

## 先把几个词说清楚

- **可恢复失败**：调用者可以提示、重试或改用其他方案
- **异常**：沿调用栈传播的失败对象
- **optional**：有一个值或没有值，不携带详细错误

## 一个案例

findTask 返回 optional<Task> 表示没找到；loadConfig 遇到格式损坏抛带文件名和原因的异常，由 main 统一输出。

```cpp
std::optional<Task> findTask(int id);

if (auto task = findTask(7))
    std::cout << task->title << '\n';
else
    std::cout << "not found\n";
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `std::optional<T>` | 表示可能没有 T |
| `std::variant` | 在有限几种类型中保存一种 |
| `throw / try / catch` | 抛出并在合适边界处理异常 |
| `assert` | 检查程序员认为必定成立的内部条件 |

## 怎么验证自己真的理解了

分别测试找到、没找到和配置损坏三条路径。每条路径都要有明确结果和退出码。

## 常见坑

- 不要 catch 后什么都不做；这会隐藏根因。
- 异常用于失败传播，不适合普通高频分支。
- assert 在发布构建中可能关闭，不能用来检查用户输入。
- 析构函数通常不能抛出异常。

## 马上动手

为一个文件加载接口写出成功、文件不存在、格式损坏三种结果的合同。

## 学完标准

能根据失败是否正常、是否需要原因、由谁处理来选择 optional、返回值或异常。
