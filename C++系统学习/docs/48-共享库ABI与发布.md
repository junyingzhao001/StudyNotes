# 48 · 共享库、ABI 与发布

[返回学习地图](../README.md) · [上一篇](47-二进制数据与字节序.md) · [下一篇](49-代码质量与持续集成.md)

## 先说这篇讲什么

这篇讲静态库、动态库、符号可见性和 ABI 风险，以及怎样向使用者发布稳定接口。

## 它有什么用

库升级后源码仍能编译，不代表旧程序二进制一定兼容。公开类布局、编译器和标准库都可能影响 ABI。

## 要解决的问题

把 private 成员直接暴露在公共头文件中，新增字段也会改变对象大小，可能破坏已有二进制调用者。

## 先把几个词说清楚

- **静态库**：链接时把需要代码复制进程序
- **动态库**：运行时由程序加载和共享
- **ABI 兼容**：不重新编译调用者仍能正确调用新版库

## 一个案例

公开 Client 只声明方法并持有 unique_ptr<Impl>。网络库和成员布局放在 cpp，减少公共头依赖和 ABI 变化。

```cpp
class Client {
public:
    Client();
    ~Client();
    void send(std::string_view);
private:
    class Impl;
    std::unique_ptr<Impl> impl_;
};
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `symbol visibility` | 控制哪些函数导出 |
| `PImpl` | 公开类只持有实现指针，隐藏布局 |
| `install/export` | 安装头文件并导出 CMake target |
| `语义化版本` | 表达兼容更新与破坏性更新 |

## 怎么验证自己真的理解了

安装库到临时目录，用一个独立小项目通过导出的 target 查找并链接。

## 常见坑

- PImpl 增加一次动态分配和间接访问，不是所有类都需要。
- 跨库边界分配和释放要使用一致合同。
- 异常、RTTI 和标准库类型跨 ABI 时需考虑工具链兼容。

## 马上动手

为一个小库设计 public/include 与 private src 边界，并列出导出符号。

## 学完标准

能解释静态/动态链接差异，并知道哪些公开变化可能破坏 ABI。
