# 43 · 综合项目：带网络同步的任务服务

[返回学习地图](../README.md) · [上一篇](42-鲁棒性与安全边界.md) · [下一篇](44-接口设计运算符与异常安全.md)

## 先说这篇讲什么

这篇把类、文件、线程、网络、测试和构建连成一个项目。重点是模块边界和验证顺序，不是堆功能。

## 它有什么用

单篇示例只能证明一个概念。综合项目让你练习修改接口后同步更新实现、协议、测试和构建。

## 要解决的问题

如果网络回调直接修改文件和业务对象，锁、失败回滚和测试都会纠缠。项目应把协议、业务、存储和 I/O 分层。

## 先把几个词说清楚

- **业务层**：只表达任务规则，不依赖 socket
- **协议层**：把字节消息转换成命令和响应
- **提交边界**：确认保存成功后才让新状态对外可见

## 一个案例

客户端发送 add。Session 校验消息后调用 TaskService；Service 先生成新状态并请求 Repository 保存，成功后提交，最后返回任务 id。

完整的分阶段任务书见 [项目三：TCP 任务服务](../projects/03-tcp-task-service/README.md)。

```text
请求: {"id":1,"command":"add","title":"learn"}
成功: {"id":1,"ok":true,"task_id":7}
失败: {"id":1,"ok":false,"error":"invalid title"}
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `TaskService` | add/complete/list 等业务接口 |
| `TaskRepository` | 持久化抽象 |
| `Session` | 一条网络连接的状态机 |
| `Executor` | 把阻塞文件操作移出 I/O 线程 |

## 怎么验证自己真的理解了

按顺序验证业务单元测试、文件失败回滚、协议解析、单连接集成测试、多连接、超时与优雅关闭。

## 常见坑

- 不要一开始就写网络层，先让业务和存储在无网络时通过测试。
- 响应错误要稳定，内部日志可更详细。
- 关闭顺序应先停止接收，再结束连接、排空任务、保存并 join。

## 马上动手

先画四层依赖图和一次 add 的时序，再创建目录；任何反向依赖都要说明原因。

## 学完标准

能独立构建、测试并解释一次请求从 socket 到持久化再返回的完整路径。
