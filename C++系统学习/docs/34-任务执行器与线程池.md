# 34 · 任务执行器与线程池

[返回学习地图](../README.md) · [上一篇](33-atomic与内存模型.md) · [下一篇](35-网络基础.md)

## 先说这篇讲什么

这篇把队列、锁、条件变量、future、异常和关闭协议组合成一个小型执行器。

## 它有什么用

业务代码不应为每个任务临时创建线程。执行器集中控制并发数量、排队、结果和关闭。

## 要解决的问题

关闭时如果仍接受任务，future 可能永远得不到结果；若立即丢队列，又要明确如何通知调用者。

## 先把几个词说清楚

- **submit**：提交任务并立即得到 future
- **背压**：队列过大时限制或拒绝新任务
- **关闭协议**：停止接收、处理/取消队列、通知、等待 worker 的约定

## 一个案例

固定两个 worker。submit 将 packaged_task 放入有上限的队列；shutdown 停止接收，排空已有任务，最后等待线程。

```cpp
auto future = task.get_future();
{
    std::lock_guard lock{mutex};
    if (stopping) throw Rejected{};
    queue.push(std::move(task));
}
cv.notify_one();
return future;
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `packaged_task` | 把任务结果连接到 future |
| `condition_variable` | 唤醒 worker |
| `jthread/vector<jthread>` | 管理固定数量 worker |
| `exception_ptr` | 必要时保存并跨边界传播异常 |

## 怎么验证自己真的理解了

测试返回值、任务异常、多生产者、队列上限、重复关闭和排空。每个并发测试都设置超时并重复运行。

## 常见坑

- 不要在持锁时执行用户任务。
- 析构中的关闭语义必须写进合同。
- 任务捕获引用时仍需保证对象活到任务完成。
- 生产级线程池还涉及取消、公平性和监控。

## 马上动手

先实现单 worker 版本，通过所有状态测试后再扩成多个 worker。

## 学完标准

能画通 submit 到 future 的数据流，并证明关闭后不会遗留可 join 线程或永远等待的 future。
