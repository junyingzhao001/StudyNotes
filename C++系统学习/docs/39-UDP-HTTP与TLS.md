# 39 · UDP、HTTP 与 TLS 的选择

[返回学习地图](../README.md) · [上一篇](38-消息边界超时与背压.md) · [下一篇](40-网络测试与可靠性.md)

## 先说这篇讲什么

这篇说明什么时候使用 UDP，什么时候直接使用成熟 HTTP/TLS 库，而不是自己实现复杂协议。

## 它有什么用

项目通常需要交换数据，不一定需要自定义 TCP 协议。HTTP 生态成熟，TLS 安全细节很多，应交给经过验证的库。本课程后续实验建议用 Boost.Beast 处理 HTTP，用 OpenSSL 提供 TLS；它们不是标准库的一部分。

## 要解决的问题

UDP 不保证到达、顺序或去重；TLS 若跳过证书和主机名校验，连接虽然加密却可能连到攻击者。

## 先把几个词说清楚

- **数据报**：UDP 一次发送的一条有边界消息
- **HTTP**：基于请求/响应的应用协议
- **TLS**：提供加密、完整性和身份校验的安全层

## 一个案例

局域网发现可用 UDP 广播；业务 API 使用 HTTPS。不要为了一个 GET 请求自己实现 HTTP 解析和证书校验。

```text
选择问题：
- 允许丢失、每条消息独立、追求低延迟？考虑 UDP。
- 需要通用 API、代理和鉴权？优先 HTTPS。
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `udp::socket send_to/receive_from` | 发送和接收 UDP 数据报 |
| `boost::beast::http` | 组织和解析 HTTP 请求、响应与字段 |
| `asio::ssl::context / stream` | 通过 OpenSSL 配置证书并建立 TLS 连接 |
| `SNI/主机名校验` | 确认服务器证书属于目标主机 |

## 怎么验证自己真的理解了

UDP 实验故意忽略一条数据报，确认业务能容忍；HTTPS 实验使用错误主机名，确认校验失败。

## 常见坑

- UDP 也有最大包和分片风险，不适合无限大消息。
- 不要关闭 TLS 证书验证来“解决”测试问题。
- HTTP 客户端还要设置连接、读取和总请求超时。

## 马上动手

为一个实际需求写选择表：可靠性、顺序、消息大小、代理、认证和安全要求。

## 学完标准

能根据需求选择 UDP、自定义 TCP 或 HTTPS，并知道安全协议应使用成熟库。
