# 35 · 网络基础与协议边界

## 先说这篇讲什么

这篇先解释 IP、端口、DNS、TCP 和 UDP，并强调 TCP 传输的是字节流，不是完整消息。

## 它有什么用

不理解消息边界，就会把一次 read 当成一条消息，遇到拆包或粘包时解析错误。

## 要解决的问题

发送方一次 write 100 字节，接收方可能分多次 read，也可能一次读到多条消息的一部分。协议必须自己定义边界。

## 先把几个词说清楚

- **IP 地址**：定位网络中的主机接口
- **端口**：定位主机上的服务
- **socket**：操作系统提供的网络通信端点

## 一个案例

聊天消息采用 4 字节长度前缀加正文。接收端先凑齐长度，再按长度凑齐正文，不能依赖 read 次数。

不依赖网络库的拆包练习见 [examples/frame_parser.cpp](../examples/frame_parser.cpp)。它把两次收到的字节重新拼成两条消息。

```text
[4 字节正文长度][正文 bytes]
[4 字节正文长度][正文 bytes]
// TCP 中两条消息可能一起到，也可能被拆开到达
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `DNS resolver` | 把域名解析成一个或多个地址 |
| `TCP` | 可靠、有序的双向字节流 |
| `UDP` | 按数据报发送，不保证到达或顺序 |
| `字节序` | 多字节整数在内存/网络中的排列方式 |

## 怎么验证自己真的理解了

用纸模拟三种到达方式：一次完整、拆成两次、两条粘在一起。解析器都应得到同样两条消息。

## 常见坑

- TCP 连接成功不代表应用协议握手成功。
- 连接关闭也可能只关闭一个方向。
- 不要直接发送 C++ 对象内存布局。

## 马上动手

为任务协议写出请求、响应、最大长度和错误消息的字节格式。

## 学完标准

能解释 TCP 为什么没有消息边界，并能设计一种明确的分帧方式。
