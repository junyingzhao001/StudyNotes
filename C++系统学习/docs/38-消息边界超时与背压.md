# 38 · 消息边界、超时、取消与背压

[返回学习地图](../README.md) · [上一篇](37-TCP客户端与服务端.md) · [下一篇](39-UDP-HTTP与TLS.md)

## 先说这篇讲什么

这篇把网络服务从“能通信”提升到“不会被半包、永久等待或无限队列拖垮”。

## 它有什么用

真实客户端可能很慢、发坏长度、突然断开或持续发送。服务端必须限制每条连接占用的时间和内存。

## 要解决的问题

若长度前缀宣称正文有 4GB，直接分配会耗尽内存；若写速度跟不上接收速度，无上限队列也会增长。

## 先把几个词说清楚

- **超时**：操作在限定时间内未完成就走失败路径
- **取消**：请求未完成操作尽快结束
- **背压**：生产速度超过消费速度时限制生产者

## 一个案例

读取长度头时启动计时器。先校验长度不超过 1MB，再分配正文；超时或队列超限则发送错误并关闭。

```cpp
timer.expires_after(5s);
timer.async_wait([self](auto error) {
    if (!error) self->socket.close();
});
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `steady_timer` | 使用单调时钟实现超时 |
| `socket.cancel/close` | 取消或结束未完成操作 |
| `最大消息长度` | 在分配前拒绝过大输入 |
| `写队列上限` | 限制每连接待发送数据 |

## 怎么验证自己真的理解了

测试半包、坏长度、慢速逐字节发送、对端断开和写队列超限。程序必须在超时后释放连接。

## 常见坑

- 超时回调与正常完成可能接近同时发生，状态转换要幂等。
- 关闭 socket 会让其他操作以错误完成，回调仍可能被调用。
- 限制应该在分配大内存之前检查。

## 马上动手

为协议写出最大包长、读超时、写队列上限和关闭顺序。

## 学完标准

能让每条连接在坏输入和慢客户端下仍有明确的资源上限与结束路径。
