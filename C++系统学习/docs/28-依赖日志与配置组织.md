# 28 · 依赖、日志与配置组织

[返回学习地图](../README.md) · [上一篇](27-调试器与Sanitizer.md) · [下一篇](29-thread与jthread.md)

## 先说这篇讲什么

这篇讲第三方库怎样进入构建，日志怎样帮助定位问题，配置怎样有明确覆盖顺序。

## 它有什么用

项目能在你电脑编译不够，还要让同事和 CI 得到相同版本。线上问题也需要日志说明何时、哪个请求、什么错误。

## 要解决的问题

依赖版本漂移会造成“我这里能跑”；日志只写“失败了”则无法定位对象和原因。下面用 `spdlog` 展示具体写法，项目也可以选择其他日志库，但要保持同样的字段和脱敏规则。

## 先把几个词说清楚

- **依赖锁定**：记录可重复取得的库版本
- **日志级别**：区分调试、信息、警告和错误
- **结构化字段**：把 request_id、path 等作为可搜索字段

## 一个案例

服务启动时输出版本和非敏感配置；每个请求带 request_id；文件错误同时记录路径和系统错误。

```cpp
spdlog::error("load failed path={} reason={}",
              path.string(), error.message());
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `FetchContent/包管理器` | 取得并配置第三方依赖 |
| `CMake target` | 通过目标传播依赖而不是手写路径 |
| `logger` | 统一时间、级别和上下文字段 |
| `配置覆盖` | 默认值、文件、环境变量、命令行的明确优先级 |

## 怎么验证自己真的理解了

从全新 build 目录构建；制造一个文件错误，确认日志足以定位路径和原因且不泄露密钥。

## 常见坑

- 不要在日志中写密码、token 或完整敏感数据。
- 不要把绝对本机路径硬编码进构建文件。
- 日志不是错误处理，记录后仍要返回或传播失败。

## 马上动手

为项目写出配置覆盖顺序，并为一次失败日志列出最少必要字段。

## 学完标准

能说明依赖版本从哪里来，并写出可定位、不过度泄露的日志。
