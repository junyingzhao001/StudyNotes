## 先说这篇讲什么

这篇介绍读写锁、一次初始化、线程局部数据、信号量、latch 和 barrier。它们解决特定模式，不替代基本锁与条件变量。

## 它有什么用

识别标准模式可以少写脆弱的计数协议，但选错工具会增加理解成本。

## 要解决的问题

读取多不代表 shared_mutex 一定更快；线程局部也可能隐藏状态并延长资源生命。

## 先把几个词说清楚

- **信号量**：限制同时进入某区域的数量
- **latch**：计数到零后一次性放行
- **barrier**：一组线程分阶段反复会合

## 一个案例

下载器最多允许 8 个并发请求，用 counting_semaphore 获取和归还名额，比手写计数加条件变量更直接。

```cpp
std::counting_semaphore<8> slots{8};
slots.acquire();
try { download(); } catch (...) { slots.release(); throw; }
slots.release();
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `shared_mutex` | 允许多个读者或一个写者 |
| `call_once/once_flag` | 保证初始化函数最多成功执行一次 |
| `counting_semaphore` | 控制有限资源名额 |
| `latch/barrier` | 协调一次性或多阶段任务 |

## 怎么验证自己真的理解了

同时启动超过 8 个任务，记录任意时刻活跃数不超过 8。实际代码应再用 RAII 包装名额归还。

## 常见坑

- 信号量许可也需要 RAII，异常路径不能漏 release。
- shared_mutex 可能有公平性和性能差异，先测量。
- thread_local 对象在线程结束前一直存在。

## 马上动手

把手写并发名额控制改成 RAII semaphore permit。

## 学完标准

能把同步需求匹配到具体工具，并知道何时继续使用普通 mutex/CV 更清楚。
