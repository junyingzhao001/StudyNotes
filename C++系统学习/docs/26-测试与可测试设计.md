# 26 · 测试与可测试设计

[返回学习地图](../README.md) · [上一篇](25-CMake与项目结构.md) · [下一篇](27-调试器与Sanitizer.md)

## 先说这篇讲什么

这篇讲把需求写成可重复检查，并通过分离业务和 I/O 让代码容易测试。

## 它有什么用

测试不仅防止回归，也迫使接口明确输入、输出和失败行为。失败时应指出哪条规则被破坏。

## 要解决的问题

如果业务逻辑直接读终端、写文件和访问时间，测试必须依赖外部环境。把纯业务放进普通函数或类，边界更容易替换。下面的 `TEST_CASE` 和 `CHECK_FALSE` 来自 Catch2 测试框架，不是 C++ 关键字。

## 先把几个词说清楚

- **单元测试**：只验证一个小单元的行为
- **集成测试**：验证多个模块或外部边界协作
- **fake**：行为可控的简化依赖实现

## 一个案例

TaskService 只依赖 TaskStore 接口。测试传入 MemoryStore，不需要真的写磁盘就能验证 add 和 complete。

```cpp
TEST_CASE("complete missing task") {
    MemoryStore store;
    TaskService service{store};
    CHECK_FALSE(service.complete(99));
}
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `Catch2 TEST_CASE` | 定义一个可独立运行的测试场景 |
| `CHECK / REQUIRE` | 验证结果；REQUIRE 失败时结束当前场景 |
| `CTest` | 统一运行 CMake 注册的测试 |
| `依赖注入` | 从外部传入存储、时钟等依赖 |

## 怎么验证自己真的理解了

先让测试因需求未实现而失败，再写最小实现使其通过。最后运行全部测试而非只运行新测试。

## 常见坑

- 不要测试 private 实现细节，应测试公开行为。
- sleep 不是可靠的并发同步测试方法。
- 测试通过只覆盖执行到的路径，不代表不存在其他错误。

## 马上动手

为正常输入、边界输入和失败输入各写一个测试。

## 学完标准

能把业务与 I/O 分开，写出失败信息清楚且可重复的测试。
