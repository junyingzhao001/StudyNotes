# 06 · 宏与条件编译

[返回学习地图](../README.md) · [上一篇](05-作用域头文件与cpp.md) · [下一篇](07-指针引用与生命周期.md)

## 先说这篇讲什么

这篇说明宏只是编译前的文本处理，并给出它适合与不适合的使用范围。

## 它有什么用

你会在跨平台代码、调试开关和头文件保护中看到宏。知道它没有类型和作用域，才能避免难调试的文本替换问题。

## 要解决的问题

函数式宏可能重复计算参数，宏常量也会把名字散到全局。多数业务逻辑用真正的 C++ 类型和函数更安全。

## 先把几个词说清楚

- **预处理器**：正式编译前处理 # 开头指令的步骤
- **条件编译**：根据构建参数决定一段代码是否进入程序
- **文本替换**：宏只替换字符，不理解类型

## 一个案例

开发版需要额外日志，发布版不需要。构建时定义 TRACE，源码用条件编译保留日志。

```cpp
#ifdef TRACE
std::cerr << "loading config\n";
#endif

inline constexpr int kMaxTasks{100};
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `#ifdef NAME` | 只有定义 NAME 时保留代码 |
| `-DNAME` | 从编译命令定义宏 |
| `constexpr` | 有类型、有作用域的常量 |
| `inline 函数/模板` | 比函数式宏更安全的计算复用 |

## 怎么验证自己真的理解了

分别用普通命令和带 `-DTRACE` 的命令构建，确认业务结果相同，只有日志不同。

## 常见坑

- 不要用 `#define SQUARE(x) x*x`；括号和重复求值都会带来问题。
- 不同 cpp 使用矛盾的宏可能看到不同类型定义，后果很难排查。
- 宏不能放进 namespace，也没有真正的参数类型。

## 马上动手

把一个宏常量改成 `inline constexpr`，把一个计算宏改成普通函数。

## 学完标准

能说出宏的合理用途，并优先用有类型的 C++ 机制表达业务逻辑。
