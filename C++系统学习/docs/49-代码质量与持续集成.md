# 49 · 代码质量与持续集成

## 先说这篇讲什么

这篇讲把格式、警告、静态分析、测试、覆盖率和模糊测试放进自动化流程。

## 它有什么用

依靠开发者记住所有检查并不可靠。CI 让每次修改在干净环境中重复同一组验证。

## 要解决的问题

格式工具不能证明正确，覆盖率高也不代表断言有效。每种工具只负责一类问题。

## 先把几个词说清楚

- **静态分析**：不运行程序也检查可疑代码
- **覆盖率**：测试执行到哪些代码的测量
- **模糊测试**：持续生成输入寻找崩溃和不变量破坏

## 一个案例

提交时依次运行格式检查、警告即错误构建、单元/集成测试、ASan/UBSan；定时任务再运行 TSan 和 fuzz。

```text
验证顺序：
格式 → 编译警告 → 单元测试 → 集成测试
     → ASan/UBSan → 静态分析 → 定期 TSan/fuzz
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `clang-format` | 统一代码排版 |
| `clang-tidy` | 检查常见缺陷和现代化建议 |
| `IWYU` | 帮助减少不必要或遗漏的 include |
| `CI matrix` | 在多编译器/配置上构建测试 |

## 怎么验证自己真的理解了

从全新 checkout 执行一条脚本，失败时返回非零退出码并指出具体步骤。

## 常见坑

- 不要一次启用大量 clang-tidy 规则却不处理结果。
- 覆盖率只说明执行，不说明验证。
- CI 中依赖版本和生成器也要固定。

## 马上动手

为课程项目写一份本地 verify 脚本，再让 CI 调用同一脚本。

## 学完标准

能说明每种质量工具负责什么，并让干净环境一键验证项目。
