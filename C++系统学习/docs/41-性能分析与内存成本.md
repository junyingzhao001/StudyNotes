# 41 · 性能分析与内存成本

## 先说这篇讲什么

这篇讲先测量再优化。你会从耗时、分配次数和数据访问方式找到真正瓶颈。

## 它有什么用

C++ 给你很多控制能力，也很容易让人凭感觉使用裸指针、缓存或无锁结构。测量能避免把复杂度花在不重要的位置。

## 要解决的问题

平均耗时可能掩盖偶发慢请求；只看 CPU 又可能忽略频繁分配、锁等待和磁盘网络时间。

## 先把几个词说清楚

- **基准测试**：在受控条件下重复测量一段代码
- **剖析器**：记录程序时间花在哪些函数或事件
- **局部性**：相关数据靠近时更容易被 CPU 缓存有效使用

## 一个案例

任务导入很慢。剖析发现大部分时间不是解析，而是 vector 反复扩容。已知行数后 reserve，使分配次数从多次降为一次附近。

```cpp
const auto start = std::chrono::steady_clock::now();
runWork();
const auto elapsed =
    std::chrono::steady_clock::now() - start;
```

## 常用 API 和作用

| API / 规则 | 用来做什么 |
| --- | --- |
| `steady_clock` | 测量经过时间，不受系统时间调整影响 |
| `benchmark library` | 预热、重复并统计结果 |
| `profiler` | 寻找热点、分配和锁等待 |
| `reserve/emplace` | 在证据支持时减少扩容或临时对象 |

## 怎么验证自己真的理解了

记录修改前后的输入规模、编译模式、机器环境、中位数和高分位耗时，不能只展示最好一次。

## 常见坑

- Debug 构建性能不能代表 Release。
- 微基准可能被编译器优化掉无用结果。
- 复杂度、可读性和内存安全通常比微小收益更重要。

## 马上动手

选择一个真实操作，先写性能假设，再用工具验证热点是否与猜测一致。

## 学完标准

能提供可复现的测量数据，并说明优化带来的收益和代码成本。
