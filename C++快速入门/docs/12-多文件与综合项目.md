# 12 · 多文件与综合项目

[返回学习地图](../README.md) · [下一篇：语法与读码速查](13-语法与读码速查.md)

## 本篇目标

理解头文件声明、源文件定义、namespace 和链接关系；读懂一个支持增删改查、文件持久化与错误恢复的任务清单 CLI。

## 学习作用

前面的 demo 各自只证明一个知识点，本篇把容器、引用、算法、异常、文件流、RAII 和多文件构建串起来。完成后，你会经历真实开发最小闭环：读接口、追实现、运行程序、修改功能、写测试、处理失败。

## Java 对照

| Java 项目中的概念 | 本项目中的 C++ 做法 | 关键差别 |
| --- | --- | --- |
| package | `namespace quickstart` | namespace 解决名字作用域，不决定文件路径 |
| interface/public class API | `.h` 里的类和函数声明 | 头文件会被预处理器包含进编译单元 |
| `.java` 类实现 | `.cpp` 函数定义 | cpp 分别编译，最后链接成程序或库 |
| import | `#include` | include 是文本层面的声明可见性，不负责链接实现 |
| Gradle module | CMake target | target 明确源文件、include 路径和链接关系 |
| JUnit test | 独立测试可执行文件 + CTest | 测试用返回码告诉构建系统成功或失败 |

不要把 package、include 和链接当成一件事。代码能够编译，仍可能因为没有链接实现而失败。

## 项目功能

命令包括：

- `add 标题`：新增非空、单行标题；
- `done 编号`：标记完成；
- `remove 编号`：删除任务；
- `list`：显示当前任务；
- `quit`：退出。

不传文件路径时，任务只在本次运行中存在。传入路径时，每次成功修改都会保存；下次使用同一路径启动即可恢复。

```bash
./build/task_cli build/my_tasks.db
```

项目刻意保持命令简单，但已覆盖非法编号、空标题、未知命令、损坏数据文件和写入失败等常见边界。

## 编译并运行

从 `C++快速入门` 目录执行：

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  project/main.cpp project/task_store.cpp project/task_file.cpp \
  -o build/task_cli
./build/task_cli
```

交互输入：

```text
add Learn references
add Build a CLI
done 1
list
remove 2
list
quit
```

也可以回放固定输入：

```bash
./build/task_cli < project/example.in
```

预期输出：

```text
Commands: add TITLE | done ID | remove ID | list | quit
Added 1
Added 2
Completed.
1 [x] Learn references
2 [ ] Build a CLI
Removed.
1 [x] Learn references
```

example.in 先 list 两项，再删除第二项并重新 list，所以最后只剩第一项。固定输入和固定输出让回归检查可以自动比较结果。

## 从入口逐步读懂

先看 main，而不是一上来阅读每个工具函数：

```text
命令行参数 DATA_FILE
        │
        ▼
如文件存在：loadTasks ──► TaskStore
                              │
用户输入一行 ──► 解析命令 ──► 在副本 updated 上修改
                              │
                    保存成功 ├──► store = move(updated)
                    保存失败 └──► 保留原 store，报告错误
                              │
                              ▼
                           打印结果
```

1. main 根据 `argc/argv` 判断是否启用持久化。如果数据文件存在，用 ifstream 打开，再交给 loadTasks。
2. getline 每次读取完整命令行，istringstream 再拆出命令和参数。和 Java 的 Scanner 相比，这种“每行单独解析”让一行坏输入不会污染下一行。
3. add/done/remove 都先复制 `store` 为 `updated`。只有 updated 保存成功，才移动回 store。这是简化的 copy-then-commit：磁盘失败时，当前内存状态不会假装修改成功。
4. `TaskStore::complete` 用 find_if 找目标；remove 用 remove_if + erase 真正缩短 vector。找不到返回 false，属于预期业务结果。
5. `tasks()` 返回 `const std::vector<Task>&`，让打印和保存只读借用容器，避免复制。调用者不能让这个引用活得比 store 更久。
6. main 内层 catch 处理单条命令失败，程序可继续；外层 catch 处理启动加载等致命失败并返回 1。

## namespace、头文件和链接

Task 与 TaskStore 放在 `namespace quickstart` 中，调用处写 `quickstart::TaskStore`。它类似 Java package 提供名字空间，但不要求目录必须同名，也不提供访问控制。

头文件声明“别人可以调用什么”，源文件定义“具体怎么做”。include guard 防止同一编译单元重复包含头文件。每个实现 cpp 首先包含自己的头文件，有助于发现头文件漏 include 依赖。main.cpp 中只在本文件使用的辅助函数放进匿名 namespace，避免产生不必要的全局外部符号。

只编译 main.cpp 会得到 TaskStore/saveTasks 等实现缺失的链接错误；正确命令必须让 task_store.cpp 与 task_file.cpp 一起参与。不要用 `#include "task_store.cpp"` 绕过多文件构建。

```bash
c++ -std=c++17 -c project/main.cpp -o build/main.o
c++ -std=c++17 -c project/task_store.cpp -o build/task_store.o
c++ -std=c++17 -c project/task_file.cpp -o build/task_file.o
c++ build/main.o build/task_store.o build/task_file.o -o build/task_cli
```

更常见的 target 化构建见 [第 15 篇](15-CMake工程化构建与测试.md)。

## 数据格式与持久化边界

数据文件每行一个任务：

```text
1 0 "Learn references"
2 1 "Build a CLI"
```

三列依次是编号、完成状态（0/1）和用 `std::quoted` 编码的单行标题。加载时会拒绝重复/非法编号、其他状态值、空标题、多行标题和多余字段。引号与反斜杠的往返由测试覆盖。

保存时先写同目录临时文件，显式 close 并检查结果，再 rename 为正式路径；main 只在保存成功后提交内存副本。这比直接截断旧文件更安全，但仍不是数据库事务，也没有处理多进程同时写入。当前替换行为面向课程推荐的 macOS/Linux/WSL 环境；原生 Windows 文件替换语义需要按平台调整。

## 三级练习

1. 预测：执行 `add A`、`add B`、`remove 1`、退出并重启后，剩余任务编号和下一次 add 编号是什么？先读测试再验证。
2. 修改：增加 `pending` 命令，只显示未完成任务；为“有待办”和“无待办”各补一个端到端输入。
3. 独立：为 Task 增加 priority。先修改数据模型与文件格式测试，再修改命令解析和显示；旧格式是拒绝、迁移还是给默认值，需要先写成明确约定。

## 完成标准

能说清 store、updated 和 tasks() 返回引用之间的所有权关系；能解释 include 成功与链接成功为何不同；能修改接口、实现、测试和 CMake target；能让保存/加载与错误输入验证全部通过。达到这些标准后，再进入第 15、16 篇补齐构建与调试，就具备参与小型实际项目的基础。
