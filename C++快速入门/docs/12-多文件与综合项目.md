# 12 · 多文件与综合项目

[返回学习地图](../README.md) · [下一篇：语法与读码速查](13-语法与读码速查.md)

## 先说结论

这一篇把前面的语言知识组合成一个可实际运行的任务清单：它支持新增、完成、删除、查看、保存和恢复。读完后，你能从 `main` 追到业务类和文件模块，理解头文件声明、cpp 定义与链接的关系，并完成一次“改接口 → 改实现 → 补测试 → 验证失败路径”的小型开发闭环。

它有用，是因为真实项目很少只有一个 cpp。能读懂文件职责、数据流和提交边界，比继续记零散语法更接近实际开发。多文件基础若仍不熟，先看 [01A · 作用域、头文件、cpp 与宏定义](01A-作用域头文件与宏定义.md)。

## 问题：功能一多，单文件会混合三类责任

任务程序同时要处理：

- 命令行输入和输出；
- 任务增删改查规则；
- 文件格式、保存和加载。

把这些全部写进 main 会让测试依赖终端和磁盘，也很难判断错误来自解析、业务还是存储。方案是按责任拆分：

```text
用户命令
   │
   ▼
main.cpp ─────► TaskStore ─────► task_store.cpp
   │             业务状态          增删改查规则
   │
   └──────────► save/load ─────► task_file.cpp
                  流接口             文件格式
```

## 方案一：头文件写合同，cpp 写实现

| 文件 | 公开或实现的责任 | 阅读重点 |
| --- | --- | --- |
| [task_store.h](../project/task_store.h) | `Task` 与 `TaskStore` 接口 | 类型、所有权、const 引用 |
| [task_store.cpp](../project/task_store.cpp) | 新增、完成、删除、编号校验 | 算法、Lambda、异常、移动 |
| [task_file.h](../project/task_file.h) | `loadTasks` / `saveTasks` 流接口 | 模块边界 |
| [task_file.cpp](../project/task_file.cpp) | 文本解析与生成 | stream、`quoted`、坏数据 |
| [main.cpp](../project/main.cpp) | 解析命令、组装模块、处理错误 | 控制流与提交时机 |
| [task_store_test.cpp](../tests/task_store_test.cpp) | 业务规则测试 | 不经过终端和磁盘 |
| [task_file_test.cpp](../tests/task_file_test.cpp) | 格式往返与坏数据测试 | stringstream 边界输入 |

Java 的 package、import、类文件可帮助建立直觉，但不能逐字对应：

| Java 概念 | C++ 中较接近的概念 | 关键差别 |
| --- | --- | --- |
| package | `namespace quickstart` | namespace 不决定目录结构 |
| public API | `.h` 中的声明 | include 会把头文件文本带入当前编译单元 |
| `.java` 实现 | `.cpp` 中的定义 | 每个 cpp 单独编译，最后链接 |
| Gradle module | CMake target | target 管理源文件、头文件路径和库关系 |

`#include` 会让头文件内容在当前编译单元可见；头文件可以包含声明，也可以包含模板或 inline 定义。普通非 inline 实现仍需由对应 cpp 或库参与链接。只编译 main.cpp 可能通过编译阶段，却在链接阶段报告 `undefined symbol/reference`。正确命令必须包含提供定义的 cpp；不要 `#include "task_store.cpp"` 来绕过构建。

## 方案二：从入口追数据，不要从第一个工具函数开始背

项目的核心路径是：

```text
可选 DATA_FILE ─► loadTasks ─► store
                                │
一行命令 ─► 解析 ─► 复制为 updated ─► 修改
                                │
                  保存成功 ─────┴──► move 回 store ─► 输出成功
                  保存失败 ─────────► 保留旧 store ─► 输出错误
```

main 使用 `getline` 每次读取完整一行，再用 `istringstream` 解析该行。这样一条坏命令不会把残留字符带到下一条命令。内层 catch 处理单条命令失败，程序继续；外层 catch 处理启动加载失败等致命错误并返回 1。

## 方案三：先保存副本，成功后再提交

如果先修改内存，再发现磁盘写入失败，界面可能显示“已经成功”，但下次启动数据又消失。项目用 copy-then-commit 避免这种不一致：

```cpp
auto updated = store;
const int id = updated.add(title);
saveIfRequested(updated, path);
store = std::move(updated);
```

只有保存成功，`updated` 才移动回正式 store。保存函数先写同目录临时文件，close 并检查后，再 rename 为目标路径。这个策略比直接截断旧文件更安全，但仍不是数据库事务，也没有解决多个进程同时写同一文件的问题；原生 Windows 的替换语义也需要单独适配。

`TaskStore::tasks()` 返回 `const vector<Task>&`，打印和保存可以只读借用而不复制。这个引用不能比 store 活得更久；若以后给 TaskStore 加并发访问，也不能把锁内取得的内部引用直接交给调用者。

## 功能约定

| 命令 | 结果 |
| --- | --- |
| `add 标题` | 新增非空、单行标题 |
| `done 编号` | 标记已有任务为完成 |
| `remove 编号` | 删除已有任务 |
| `list` | 按当前顺序显示任务 |
| `quit` | 结束程序 |

不传路径时数据只存在于本次进程；传入路径时，成功修改会保存，下次用同一路径启动即可恢复。文件每行包含编号、0/1 完成状态和 `std::quoted` 标题；加载时会拒绝重复或非法编号、非法状态、空/多行标题及多余字段。

## 验证：先跑固定输入，再跑持久化

从课程目录执行：

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  project/main.cpp project/task_store.cpp project/task_file.cpp \
  -o build/task_cli
./build/task_cli < project/example.in
```

预期输出：

```text
Commands: add TITLE | done ID | remove ID | list | quit
Added 1
Added 2
Completed.
1 [x] Learn references
2 [ ] Build a CLI
Removed.
1 [x] Learn references
```

再运行完整验证：

```bash
bash scripts/run_all.sh
SANITIZE=1 bash scripts/run_all.sh
```

脚本会检查正常命令、非法输入、单元测试、损坏文件、保存失败回滚，以及两个独立进程之间的持久化。ASan/UBSan 能发现部分内存和未定义行为问题，但不能证明所有路径正确，也不检测普通数据竞争。

## 局限与常见坑

- namespace 管理名字，不负责文件可见性、链接或访问控制。
- 头文件声明正确，不代表对应 cpp 已进入链接命令或 target。
- 返回内部容器引用减少复制，也把生命周期约束交给调用者。
- `remove_if` 后必须 erase，相关迭代器随修改失效。
- copy-then-commit 会复制当前任务列表，适合本课程规模；大数据或数据库需要不同事务设计。
- 临时文件加 rename 降低损坏风险，但不提供多进程锁、崩溃一致性或跨平台完全相同的替换语义。

## 三级练习

1. 预测：执行 `add A`、`add B`、`remove 1`，重启后剩余编号是什么，下一次 add 得到几号？先读测试再验证。
2. 修改：增加 `pending` 命令，只显示未完成任务；为“有待办”和“无待办”各补一个固定输入。
3. 独立：给 Task 增加 priority。先决定旧文件是拒绝、迁移还是使用默认值，再修改模型、格式、命令、显示和测试。

## 完成标准

能从 main 追到业务与文件模块；能解释声明、定义、编译和链接的关系；能说清 store、updated 和 `tasks()` 引用的所有权；能修改接口、实现、测试及构建配置，并让成功与失败验证都通过。
