## 先说结论

**真实问题：** 一个简单计数器也会因并发读改写产生数据竞争，但为单个独立数值设计一整套复合锁协议有时没有必要。

**读完你能做什么：** 用 `std::atomic` 安全更新独立计数器或状态标志，区分一次原子操作和多步业务事务，并避免把 C++ `volatile` 当成线程同步。

**为什么有用：** 请求数、完成数和简单开关经常由多线程访问。atomic 能准确解决“单个值的一次操作”，知道它的边界与会用它同样重要。

## 问题：只想加一，也可能发生数据竞争

普通 `++counter` 是读、改、写的组合。多线程同时执行时会冲突。第 18 篇可以用 mutex 保护它；如果状态确实只是一个彼此独立的数值，也可以让这个读改写操作本身成为原子操作。

把 atomic 想成入口处的机械计数器：每个人按一下，数字增加一次，不会有两次按压覆盖彼此。但它只能保证这个计数动作；它不能同时替你更新“人数、票款、最后一张票号”三栏账本。

## 方案：对单个值使用 atomic 操作

```cpp
std::atomic<int> counter{0};

// 多条线程可以执行：
counter.fetch_add(1);

// join 后读取：
int value = counter.load();
```

`++counter` 也是原子的读改写。`load()` 和 `store()` 分别进行原子读取与写入。

但下面写法不是一个整体的原子递增：

```cpp
counter = counter + 1;
```

右侧先做一次原子 load，左侧再做一次原子 store，其他线程可以插入两者之间。需要原子递增时使用 `++counter` 或 `fetch_add(1)`。

## Java 对照：AtomicInteger 最接近

| Java | C++17 | 需要记住的差别 |
| --- | --- | --- |
| `AtomicInteger.incrementAndGet()` | `++counter` | 都执行原子读改写 |
| `AtomicInteger.getAndIncrement()` | `counter.fetch_add(1)` | 都返回修改前的值 |
| `AtomicInteger.get()/set()` | `load()/store()` | 都原子访问单个值 |
| Java `volatile` | 不能直接翻译成 C++ `volatile` | C++ volatile 不是线程同步工具 |
| `synchronized` 或 `Lock` | `std::mutex` | 多字段不变量通常仍需锁 |

Java `volatile` 带有语言定义的线程可见性与顺序规则；C++ `volatile` 主要用于特殊内存访问，不能修复数据竞争。Java 背景下最安全的迁移方式是先问：“这里需要的是 AtomicInteger，还是一把保护业务事务的锁？”

## atomic 能保证什么，不能保证什么

一个 atomic 操作不会被其他线程观察为“执行到一半”。这适合：

- 独立请求计数。
- 独立完成计数。
- 有完整停止协议配合的简单状态标志。

下面这些通常仍需要 mutex：

- “余额足够才扣款”这种先检查再修改。
- 同时更新 `balance` 和 `lastTransactionId`。
- `vector.push_back`、`map.erase` 等容器结构修改。
- 需要一致快照的多个字段。

即使两个字段各自都是 atomic，也只保证每个字段的单次操作；读者仍可能看到“新余额 + 旧流水号”的组合。atomic 不会自动把多步操作变成事务。

atomic 也不管理生命周期。`atomic<T*>` 只能原子地读写指针值，无法保证目标对象仍然存在。

## 先使用默认内存顺序

本篇所有 atomic 操作都使用默认的顺序一致语义。可以先把它理解为：所有线程对这些原子操作能够形成一个共同认可的先后顺序。

`memory_order_relaxed`、acquire/release 等允许减弱顺序约束，但正确性依赖完整的内存模型推理。入门阶段不要仅凭“可能更快”就改内存顺序；先使用默认值，等真实项目有性能证据和评审条件再深入。

## 验证：四条线程共同计数

完整源码：[demos/21.cpp](../demos/21.cpp)

关键并发部分：

```cpp
std::atomic<int> counter{0};
{
    std::vector<std::thread> workers;
    JoiningThreads joining{workers};
    // 每条线程循环执行 ++counter
} // RAII guard 在这里 join 全部线程
```

`JoiningThreads` 的完整实现保留在 demo 中。它让线程先于 `counter.load()` 完成，也能在线程创建中途抛异常时收尾已创建线程。

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/21.cpp -o build/demo_21
./build/demo_21
```

预期输出：

```text
counter: 20000
```

每次递增都是原子操作，main 又在全部 join 后读取，因此输出确定。

## 局限与常见坑

- `volatile int` 不能替代 atomic，也不能修复数据竞争。
- `counter = counter + 1` 不是一次不可分割的递增；使用 `++` 或 `fetch_add`。
- atomic 成员不代表围绕它的整个类线程安全。
- 两个 atomic 不会自动维护跨字段不变量。
- atomic 指针不拥有目标对象，也不解决悬空指针。
- 不要在没有测量和评审时随意选择较弱的 memory order。
- ASan/UBSan 不检测普通数据竞争；ThreadSanitizer 需要单独构建，并且不能和 ASan 混在同一次构建中。

## 三级练习与完成标准

1. **预测：** 四条线程的循环次数分别改为 1、2、3、4，最终计数是多少？为什么调度顺序不影响它？
2. **修改：** 用 `fetch_add(1)` 替换 `++counter`，并打印一次返回的旧值，理解它与新值的区别。
3. **设计：** 账户包含 `balance` 和 `lastTransactionId`。解释两个 atomic 为什么不能维护“一次交易同时更新两个字段”，再给出 mutex 方案。

完成标准：能判断独立单值何时适合 atomic、复合状态何时需要 mutex，能区分原子读改写和分开的 load/store，并明确 C++ volatile 与线程同步无关。
