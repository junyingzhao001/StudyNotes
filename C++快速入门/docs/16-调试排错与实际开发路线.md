# 16 · 调试排错与实际开发路线

[返回学习地图](../README.md) · [下一篇：线程创建与生命周期](17-线程创建与生命周期.md)

## 先说结论

这一篇解决“程序不对时，从哪里开始查”的问题。读完后，你会按错误阶段选择编译器诊断、测试、LLDB 或 Sanitizer，并能把修复结果变成可重复验证。

这项能力比记住更多语法更接近实际开发。C++ 问题可能发生在编译、链接、业务逻辑、对象生命期或线程同步阶段；工具选错时，会在无关信息里花很多时间。

## 问题：相似现象可能来自完全不同的阶段

先分类，再调试：

| 现象 | 常见原因 | 第一工具 |
| --- | --- | --- |
| 编译失败 | 类型不匹配、名字不可见、模板实参错误 | 第一条指向自己源码的编译诊断 |
| 链接失败 | cpp/库未进入 target、重复定义 | 链接器错误与 CMake target |
| 测试失败 | 条件、状态转换或预期错误 | 最小失败输入、断言附近状态 |
| 抛出异常 | 显式错误边界、`at()` 越界 | 异常信息与调用栈 |
| 崩溃或偶发错值 | 越界、悬空、未定义行为 | Sanitizer + 调试器 |
| worker 不退出 | 停止状态、通知、谓词或 join 缺失 | 超时、调试器线程栈/状态、受控测试；怀疑数据竞争时再用 TSan |
| 只在 Release 出错 | 未定义行为、时序假设、优化暴露问题 | Sanitizer、最小复现、配置对比 |

Java 数组越界通常抛 `ArrayIndexOutOfBoundsException`；C++ 的 `vector::operator[]` 越界是未定义行为，可能崩溃、输出错误值，也可能暂时看似正常。“这次没崩”不是有效验证。

## 方案：固定使用“复现 → 定位 → 修复 → 防回归”

```text
保存最小失败输入
      ↓
确认期望与实际差异
      ↓
按阶段选工具，找到错误第一次出现的位置
      ↓
只修根因
      ↓
新增能覆盖旧错误的测试，再跑相关与完整验证
```

具体执行顺序：

1. 保存可重复的最小输入，同时写下期望和实际结果。
2. 从第一条与自己源码有关的编译错误或栈帧开始，不从最后一屏猜。
3. 启用警告和 Debug 信息，先运行范围最小的相关测试。
4. 在错误值第一次出现的位置附近设断点，查看参数、局部变量和调用栈。
5. 怀疑越界、释放后使用等问题时，用 ASan/UBSan 跑同一输入。
6. 修复后补回归测试，再运行完整验证；并发问题还要使用确定的 gate/状态，不能靠 sleep 猜时序。

## 验证一：用 LLDB 找逻辑条件错误

[debug_lab.cpp](../labs/debug_lab.cpp) 要找“第一个至少达到 90 的分数”，当前条件却使用 `>`，所以输入 `60, 90` 会输出：

```text
not found
```

先编译并启动 LLDB：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  labs/debug_lab.cpp -o build/debug_lab
lldb ./build/debug_lab
```

关键操作：

```text
breakpoint set --file debug_lab.cpp --line 7
run
frame variable index threshold
expression scores[index]
continue
frame variable index threshold
expression scores[index]
continue
quit
```

当 `scores[index]` 等于 threshold 时，条件仍为 false，由此定位到边界比较。把 `>` 改为 `>=` 后，预期输出是：

```text
found index: 1
```

Sanitizer 不会报告这种业务逻辑错误；需求和测试预期才会暴露它。

## 验证二：用 Sanitizer 找越界

[sanitizer_lab.cpp](../labs/sanitizer_lab.cpp) 故意读取 `scores[3]`，而容器只有三个元素。它只用于工具练习：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  labs/sanitizer_lab.cpp -o build/sanitizer_lab
./build/sanitizer_lab
```

报告很长时，先找错误类型，再找第一处指向 `sanitizer_lab.cpp` 的栈帧和行号。修复方式是保证下标小于 `scores.size()`，或者在业务边界使用 `at()` 获得可处理的越界异常。

课程正常路径可以统一验证：

```bash
bash scripts/run_all.sh
SANITIZE=1 bash scripts/run_all.sh
```

ASan 主要发现越界、释放后使用等内存错误，UBSan 覆盖部分未定义行为。它们只检查实际执行到的路径，也不能替代断言和代码审查。普通数据竞争需要单独使用 ThreadSanitizer；可选练习见 [第 18 篇](18-数据竞争与互斥锁.md)，并且 TSan 不能与 ASan 放在同一构建中。

## 进入陌生项目：从可执行目标向下追

不要一开始顺序阅读所有文件。先确认构建入口和一个可观察行为：

```text
README / CMakePresets
        ↓
可执行 target 或失败测试
        ↓
main / 公开接口
        ↓
具体 cpp 实现
        ↓
值、引用、所有权、错误和同步边界
```

1. 先按项目说明成功构建未修改版本。
2. 找到相关可执行 target 或测试，从 main/失败断言向下追。
3. 遇到接口先读头文件，遇到行为再跳 cpp。
4. 修改最小范围，先跑相关测试，再跑完整验证。
5. 提交前运行项目要求的格式化、静态检查、警告和测试；常见工具有 clang-format、clang-tidy，但以项目配置为准。

## 学完后能做什么

完成 00–16 与任务项目练习后，你应该能：

- 构建小型 C++17 项目，区分编译和链接失败；
- 追踪值、引用、指针、RAII、容器和算法代码；
- 在已有项目中定位入口、修改普通功能并补测试；
- 排查常见异常、越界、悬空和文件错误；
- 看懂基础 CMake target 与依赖关系。

继续完成 17–22、能追踪并修改现有 TaskExecutor，并独立写出由 main 负责关闭的简化版后，你还应能创建和正确结束普通工作线程，使用 mutex、condition_variable、atomic 和 future，并读懂单 worker 的排空关闭协议。

## 能力边界与后续路线

这些能力足以让你在代码评审和现有测试保护下参与小型项目，但不等于能独立设计生产级 C++ 基础设施。

| 方向 | 下一步重点 |
| --- | --- |
| Android JNI/NDK | JNI 引用与线程、Gradle/CMake native 配置、ABI、字符与数组边界 |
| 后端/网络 | 网络库、序列化、并发、超时和错误模型 |
| 图形/游戏 | 数学、资源生命期、渲染 API、性能分析 |
| 桌面 GUI | 框架对象模型、事件循环和 UI 线程规则 |
| 通用库 | API/ABI、兼容性、测试矩阵和包发布 |

第 17–22 篇覆盖并发入门。生产线程池、取消、超时、背压、多 worker 调度、正式内存模型、协程、无锁结构和并发性能分析仍要结合项目继续学习；模板元编程、分配器和 ABI 细节也按实际需求补充。

## 局限与常见坑

- 一次无法复现的现象不能直接证明根因；先保存环境、输入和配置。
- 不要修完一个症状就删除失败用例；把它变成回归测试。
- ASan/UBSan 没有报告，不代表没有逻辑错误、未执行路径或数据竞争。
- Release 与 Debug 行为不同，优先怀疑错误假设和未定义行为，不要依赖未初始化值“碰巧可用”。
- 调试器能显示当前状态，但状态为什么不符合业务要求仍要靠接口约定和测试判断。

## 三级练习

1. 预测：debug_lab 中分数恰好等于阈值时，`>` 和 `>=` 分别返回什么？
2. 修改：用 LLDB 定位并修复 debug_lab，再写下断点处的 index、threshold 和 score。
3. 独立：给任务项目增加 `pending` 命令和测试；先制造一个旧代码必失败的检查，再实现功能，最后运行普通与 Sanitizer 两套验证。

## 完成标准

能先分类错误再选择工具；能用 LLDB 找到条件第一次出错的位置；能读懂 Sanitizer 报告的首个项目栈帧；修复后会增加回归测试并跑完整验证。并发阶段还应能解释为什么测试不能依赖 sleep 或线程输出顺序。

## 马上动手
