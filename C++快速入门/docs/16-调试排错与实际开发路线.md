# 16 · 调试排错与实际开发路线

[返回学习地图](../README.md) · [下一篇：线程创建与生命周期](17-线程创建与生命周期.md)

## 本篇目标

形成一套可重复的排错流程，会使用警告、测试、LLDB 和 Sanitizer，知道学完课程后能做什么、还需要按项目方向补什么。

## 学习作用

实际开发不是把所有语法背完再开始，而是反复经历“理解需求 → 找到入口 → 修改最小范围 → 构建 → 测试 → 调试”。排错能力决定你能否在陌生项目里稳定推进。

## Java 对照

Java 常从异常堆栈、IDE 断点和单元测试定位问题；C++ 也使用这些手段，但还要处理编译、链接、未定义行为和对象生命周期。

| 现象 | 例子 | 第一工具 |
| --- | --- | --- |
| 编译失败 | 类型不匹配、名字未声明 | 看第一条指向自己源码的诊断 |
| 链接失败 | undefined symbol/reference | 查实现 cpp 或库是否进入 target |
| 测试失败 | 输出/状态不符合预期 | 缩小输入，检查断言附近状态 |
| 抛出异常 | at 越界、显式 throw | 异常信息、调用栈、失败输入 |
| 崩溃或偶发错误 | 悬空、越界、数据竞争 | Sanitizer + 调试器 |
| 只在 Release 出错 | 未定义行为、时序、错误假设 | Sanitizer、最小复现、比较配置 |

Java 的 ArrayIndexOutOfBoundsException 通常稳定抛出；C++ 的 vector `operator[]` 越界是未定义行为，可能没有异常。调试 C++ 时，“这次没崩”不能证明地址使用正确。

## 一套固定排错顺序

1. 保存能稳定复现的最小输入，并记录期望结果和实际结果。
2. 从第一条与自己代码有关的编译错误或栈帧开始，不从最后一屏猜。
3. 打开高等级警告，使用 Debug 构建，先跑相关的最小测试。
4. 在错误值第一次出现的位置附近设断点，检查参数、局部变量和调用栈。
5. 怀疑越界、释放后使用等内存错误时，用 AddressSanitizer/UndefinedBehaviorSanitizer 重跑同一输入。
6. 修复根因后补一个能在旧代码上失败、在新代码上通过的测试，再跑完整验证。

## LLDB 练习

[debug_lab.cpp](../labs/debug_lab.cpp) 的需求是找到“至少达到阈值”的第一个分数，但当前普通运行会错误地输出 `not found`：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  labs/debug_lab.cpp -o build/debug_lab
./build/debug_lab
lldb ./build/debug_lab
```

进入 LLDB 后逐条输入：

```text
breakpoint set --file debug_lab.cpp --line 7
run
frame variable index threshold
expression scores[index]
continue
frame variable index threshold
expression scores[index]
quit
```

看到 score 等于 threshold 时，检查条件为什么仍为 false。把 `>` 改成 `>=` 后，预期输出为 `found index: 1`。这类逻辑错误不会被 Sanitizer 发现，测试中的期望结果才会暴露它。

## Sanitizer 练习

[sanitizer_lab.cpp](../labs/sanitizer_lab.cpp) 故意越界，仅用于工具练习：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  -fsanitize=address,undefined -fno-omit-frame-pointer \
  labs/sanitizer_lab.cpp -o build/sanitizer_lab
./build/sanitizer_lab
```

报告很长时先找错误类型，再找第一处指向 sanitizer_lab.cpp 的栈帧和行号。修复方式是让下标小于 `scores.size()`，或者在业务上使用 `at()` 获得可处理的越界异常。课程全部正常路径也可以用 `SANITIZE=1 bash scripts/run_all.sh` 检查。

## 进入真实仓库时怎么读

1. 读根目录 README、构建预设和贡献说明，先成功构建原代码。
2. 找可执行目标或测试目标，再从 main、入口函数或失败测试向下追。
3. 遇到接口先读头文件，遇到行为再跳到 cpp；追踪传入的是值、引用、指针还是智能指针。
4. 先运行与修改相关的测试，再改一个最小行为；不要同时重构无关部分。
5. 在提交前运行格式化、静态检查和项目要求的完整测试。具体工具以仓库配置为准，常见有 clang-format、clang-tidy 和编译器警告。

## 学完后的能力边界

完成 00–16、独立做完任务项目的两个扩展，并能写测试后，你应该可以：

- 构建和运行小型 C++17 项目；
- 读懂常见值、引用、指针、RAII、容器和算法代码；
- 在已有小型项目中定位入口、修改普通功能、补测试；
- 排查常见编译、链接、异常、越界和生命周期问题；
- 看懂基础 CMake target 关系，并接入项目已有依赖。

继续完成 17–22 并独立重写 TaskExecutor 后，你还应该可以：

- 创建和正确结束普通工作线程，判断捕获对象是否活得足够久；
- 识别数据竞争，用 mutex、condition_variable 或 atomic 保护对应状态；
- 用 future 获取异步结果与异常；
- 读懂并修改常见的单 worker、任务队列和排空式关闭代码。

这代表具备开始实际项目开发的基础，不等于能独立负责生产级 C++ 系统。还需按方向继续学习：

| 项目方向 | 下一步重点 |
| --- | --- |
| Android JNI/NDK | JNI 引用与线程、CMake/Gradle native 配置、ABI、字符串和数组边界 |
| 后端/网络 | 网络库、序列化、并发、超时与错误模型 |
| 图形/游戏 | 数学、资源生命周期、渲染 API、性能分析 |
| 桌面 GUI | 所选框架的对象模型、事件循环和线程规则 |
| 通用库 | API/ABI、兼容性、文档、测试矩阵和包发布 |

第 17–22 篇覆盖 thread、mutex、condition_variable、async/future、atomic 默认操作和一个最小执行器。生产线程池、任务取消、超时、背压、多 worker 调度、正式内存模型、memory_order、协程、无锁结构与并发性能分析仍应结合具体项目继续学习。模板元编程、分配器和 ABI 细节也按项目需要补充。

## 完成标准

不看步骤完成一次调试：复现 debug_lab 的错误，设断点找到错误条件，修复并写下验证结果。然后给任务项目增加一个 `pending` 命令和相应测试，运行普通与 Sanitizer 两套验证。能完成这两项，就已经从“看懂 demo”跨到了“按需求修改项目并证明修改正确”。

并发阶段再完成一次独立复现：不看源码写出带谓词等待和 drain 关闭语义的单 worker 队列，验证正常结果、任务异常、FIFO、重复关闭和析构排空。能解释测试为什么不依赖 sleep 或线程输出顺序，才算真正掌握第 17–22 篇。
