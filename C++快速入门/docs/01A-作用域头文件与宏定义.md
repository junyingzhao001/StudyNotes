# 01A · 作用域、头文件、cpp 与宏定义

[返回学习地图](../README.md) · [上一篇：编译运行与程序结构](01-编译运行与程序结构.md) · [下一篇：类型初始化与常用语法](02-类型初始化与常用语法.md)

## 先说结论

这篇解决一个很快就会遇到的问题：代码拆成多个文件后，名字应该在哪里可见，声明和实现分别放哪里，`#include` 与 `#define` 到底做了什么。

读完你应该能把一个功能正确拆成 `.h + .cpp + main.cpp`，看懂作用域和匿名 namespace，使用 include guard 与条件编译，并知道普通常量和函数为什么通常不该写成宏。这些能力直接决定你能否读懂真实项目目录，以及能否定位“找不到名字、重复定义、链接不到实现”三类常见错误。

## 问题：一个 cpp 为什么很快就不够用

假设程序要把用户分数限制在 0–100。只有 main.cpp 时，把函数随手写在 main 上方也能运行；测试、命令行程序和其他模块都要调用它时，继续复制代码会产生三个问题：

- 每份副本可能改得不一样；
- 所有辅助名字都暴露给调用者，容易冲突；
- 调用者不知道哪些是稳定接口，哪些只是实现细节。

解决办法是公开一份小合同，把实现和内部辅助逻辑藏在 cpp 中。

## 方案一：h 放合同，cpp 放实现

可以把头文件想成餐厅菜单：它告诉调用者“能点什么、怎么点”，但不会把厨房步骤全部印出来。cpp 像厨房实现；main.cpp 只依赖菜单。

| 文件 | 适合放什么 | 不适合放什么 |
| --- | --- | --- |
| `.h` | 类型定义、函数声明、必要的常量、模板 | 只被一个 cpp 使用的辅助函数、可随意改变的实现细节 |
| `.cpp` | 普通函数定义、私有辅助逻辑 | 其他 cpp 必须看见才能编译的声明 |
| `main.cpp` | 组装对象、处理输入输出、调用业务接口 | 所有业务实现 |

[score.h](../structure_demo/score.h) 公开的关键合同只有两项：

```cpp
namespace quickstart {
inline constexpr int kMaxScore{100};
int normalizeScore(int score);
}
```

函数声明说明名字、参数和返回类型；[score.cpp](../structure_demo/score.cpp) 提供唯一的普通函数定义。`inline constexpr` 让有类型、有 namespace 作用域的编译期常量可以安全放在 C++17 头文件中。

Java 类比只能帮助入门，不能逐字对应：`.h` 有点像公开 API，`.cpp` 有点像实现类；但 `#include` 不是 import。预处理器会把头文件文本展开进当前 cpp，编译器随后分别编译每个 cpp。

项目自己的头文件通常写成 `#include "score.h"`，标准库或已配置到编译器搜索路径的库通常写成 `#include <iostream>`。两种写法会影响常见的搜索顺序，具体目录仍由编译器和构建配置决定。只 include 头文件；不要写 `#include "score.cpp"`。cpp 应作为独立源文件参与编译，最后由链接器组合。

```text
main.cpp  + 展开的 score.h ──编译──► main.o
score.cpp + 展开的 score.h ──编译──► score.o
                                     │
                         main.o + score.o ──链接──► 程序
```

因此，include 了 score.h 只代表 main.cpp 看见声明。若链接命令漏掉 score.cpp，编译可能成功，链接仍会报 undefined symbol/reference。

## 方案二：用作用域控制名字能在哪里使用

作用域回答“这个名字在代码的哪些位置可见”。生命周期回答“这个对象在运行时活到什么时候”。局部对象常常在离开大括号时同时失去名字并被销毁，所以二者容易被混为一谈，但它们不是同一个概念。

| 作用域 | 典型用途 |
| --- | --- |
| `{ ... }` 块作用域 | 限制临时变量和 RAII 资源的使用范围 |
| 函数作用域 | 参数与局部变量只服务一次调用 |
| 类作用域 | 把状态和行为放进同一类型 |
| 命名 namespace | 组织公开名字，避免不同库同名冲突 |
| 匿名 namespace | 让名字只在当前 cpp 内可见 |

score.cpp 中的辅助函数不属于公开接口：

```cpp
namespace {
int clampAtLeastZero(int score) {
    return score < 0 ? 0 : score;
}
}
```

匿名 namespace 像 Java 类中的 private 辅助方法，但限制单位是当前 cpp。其他 cpp 即使写出同名函数，也不会与它发生链接名字冲突。

避免在内层作用域重复声明同名变量。它会遮住外层名字，代码看起来仍合理，实际修改的却可能是另一份数据。头文件中也不要写 `using namespace std;`，因为每个 include 它的文件都会被迫引入这批名字。

## 方案三：把宏限制在预处理职责内

宏在正式编译前由预处理器处理。它只做文本层面的工作，不理解类型、namespace 或函数调用。

本例的 include guard 是宏的合理用途：

```cpp
#ifndef CPP_QUICKSTART_SCORE_H
#define CPP_QUICKSTART_SCORE_H
// 头文件内容
#endif
```

同一编译单元间接 include 两次 score.h 时，第二次会被跳过，避免重复声明内容。`#pragma once` 也很常见且受到主流编译器支持，但 include guard 完全由标准预处理机制表达。

另一个合理用途是按构建配置决定是否编译一段代码：[main.cpp](../structure_demo/main.cpp) 只有在定义 `QUICKSTART_TRACE` 时才输出跟踪信息。

```cpp
#ifdef QUICKSTART_TRACE
std::cout << "trace: raw=135, max=" << quickstart::kMaxScore << '\n';
#endif
```

不要用宏代替普通常量或函数：

```cpp
#define MAX_SCORE 100       // 没有类型，也没有 namespace
#define SQUARE(x) x * x     // SQUARE(1 + 2) 会被错误展开
```

对应的 C++ 方案更安全：常量用 `constexpr`，固定类型函数用普通函数，泛型逻辑用函数模板，有限选项用 `enum class`。编译器能检查类型、作用域和参数求值，调试器也更容易显示真实名字。

## 一个定义规则：为什么有时重复定义

可以先记住入门版规则：普通的非 inline 函数通常在整个程序中只定义一次，声明可以被多个 cpp 看见。把普通函数实现直接写进公共头文件，两个 cpp include 后可能生成两份外部定义，链接器就会报告 duplicate symbol/multiple definition。

类定义、模板和 inline 函数有专门规则，通常需要把完整定义放在头文件，并保证每处看到的定义一致。遇到这类代码先遵循项目现有写法，不要为了“减少 cpp”随意移动定义。

## 验证：分别证明声明、链接和条件编译

完整示例在 [structure_demo](../structure_demo)。从课程目录执行：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  structure_demo/main.cpp structure_demo/score.cpp \
  -o build/header_source_demo
./build/header_source_demo
```

正常输出：

```text
normalized: 100
```

再通过 `-D` 定义构建宏：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g \
  -DQUICKSTART_TRACE \
  structure_demo/main.cpp structure_demo/score.cpp \
  -o build/header_source_trace_demo
./build/header_source_trace_demo
```

这次多一行：

```text
normalized: 100
trace: raw=135, max=100
```

验证错误时一次只改变一件事：链接命令删掉 score.cpp，会得到缺少实现的链接错误；main.cpp 删掉 score.h，会得到名字不可见的编译错误。恢复后再运行正确命令。

## 容易翻车的地方

- 头文件依赖某个类型却没有 include 对应头文件，只因别处碰巧先 include 才能编译。
- 在头文件定义普通全局变量或普通非 inline 函数，引发多重定义。
- 把 `#include` 当成链接库，漏掉提供实现的 cpp 或 target。
- 用宏常量污染全局名字，或用函数式宏让参数被重复求值。
- 不同 cpp 使用互相矛盾的编译宏，导致它们看到不同的类布局或声明。
- 混淆作用域和生命周期，以为“名字看不见”就代表对象一定已经销毁。

## 三级练习

1. 预测：编译命令保留 main.cpp、删除 score.cpp，会在哪个阶段失败？为什么？
2. 修改：在 score.h 声明 `bool isPassingScore(int)`，在 score.cpp 定义为分数至少 60，并从 main 调用。
3. 独立：增加 `report.h/report.cpp`，让它返回一段成绩描述；内部辅助函数放匿名 namespace，并为 Debug 输出增加一个条件编译开关。

## 完成标准

能区分作用域与生命周期、声明与定义、include 与链接；能说明 h 和 cpp 各自承担什么；能用 include guard 防止重复展开，用 `constexpr` 或函数替代普通业务宏，并通过编译参数控制条件编译。
