# 11 · 错误处理与文件读写

[返回学习地图](../README.md) · [下一篇：多文件与综合项目](12-多文件与综合项目.md)

## 先说结论

这一篇解决“操作失败时，程序应该怎样把失败说清楚”的问题。读完后，你能用 `optional` 表示正常缺失，用异常表示当前操作无法完成，并正确检查文件打开、写入、关闭和读取结果。

这很有用，因为能跑通成功路径只完成了一半。用户漏传参数、查询没有结果、目录不存在或磁盘写入失败，都是实际项目必须处理的输入，而不是可以忽略的意外。

## 问题：不同失败不应该混成同一个值

贯穿本篇的是一个小型成绩文件程序：它接收一个新文件路径，写入说明，再读回内容；一次成绩查询可能没有结果。

这些情况含义不同：

| 情况 | 推荐表达 | 调用者应做什么 |
| --- | --- | --- |
| 查询不到是正常结果 | `std::optional<T>`、bool、迭代器 end | 检查后选择备用行为 |
| 参数违反接口约定 | 异常或项目统一错误类型 | 修正输入或在边界报告错误 |
| 文件操作失败 | 检查流状态，必要时转成异常 | 停止当前操作，不提交半成品 |
| 整个进程失败 | `main` 返回非 0 | 让脚本、终端或 CI 识别失败 |

不同项目可能使用异常、错误码或 expected 风格类型。进入已有代码库时先遵循现有约定，不要在同一层随意混用。

## 方案一：用 optional 表示“可以没有”

`std::optional<int>` 表示“这里可能有一个 int”。`firstScore(false)` 返回 `std::nullopt`，这是正常查询结果，不必抛异常。

使用 `value_or(0)` 可以提供备用值；调用 `.value()` 或 `*score` 前则必须确认有值。optional 只能说明“有没有值”，若还要解释失败原因，需要更丰富的错误类型。

Java `Optional<T>` 的用途接近。差别是 Java 基本类型常有 OptionalInt 等专用类型，而 C++ 可以直接写 `optional<int>`。

## 方案二：在程序边界处理异常

参数错误、无法创建文件等情况会中断当前操作。[完整 demo](../demos/11.cpp) 的关键边界是：

```cpp
try {
    if (argc != 2) {
        throw std::invalid_argument("usage: demo NEW_OUTPUT_FILE");
    }
    // 完整 demo 在此之前还检查了“目标文件不存在”。
    std::ofstream output(argv[1]);
    if (!output) throw std::runtime_error("cannot open output");
    output << "C++17 file demo\n";
    output.close();
    if (!output) throw std::runtime_error("cannot finish writing");
} catch (const std::exception& error) {
    std::cerr << "error: " << error.what() << '\n';
    return 1;
}
```

按 `const std::exception&` 捕获可以避免复制，并保留派生异常的多态信息。异常传播时，已经完整构造的局部对象会依次析构，这正是 RAII 能在失败路径释放资源的原因。

Java checked exception 会强制出现在方法声明或 catch 中；C++ 没有对应的编译期强制检查。Java try-with-resources 明确管理资源作用域，C++ 文件流离开作用域会自动析构，但写入是否真正完成仍要检查 close/flush 阶段的状态。

## 方案三：文件流每个关键阶段都要验证

fstream 默认通过状态位报告多数错误，并不会在每次失败时自动抛异常。可靠的顺序是：

```text
验证参数 → 打开输出流 → 写入 → close/检查
         → 打开输入流 → getline 读取 → 判断是否正常到达 EOF
```

逐行读取使用 `while (std::getline(input, line))`。不要写 `while (!input.eof())`，因为 EOF 只有在一次读取尝试到达末尾后才会被设置，容易多处理一次无效内容。

循环结束也不自动代表成功：正常到达文件尾会设置 eof；`bad()` 常表示更严重的底层错误；`fail()` 且不是 EOF 也应视为读取失败。

相对路径基于程序运行时的工作目录，不是 cpp 文件所在目录。程序先检查 `filesystem::exists` 再打开，只是课程中的防覆盖措施；“检查后再创建”存在并发窗口，不是安全的独占创建协议。

## 局限与常见坑

- `score.value()` 在空 optional 上会抛异常，`*score` 在空 optional 上没有有效值可读。
- catch 后不要吞掉错误并返回成功；进程边界要给出非 0 状态。
- 打开成功不代表最终写盘成功，写入和 close 后仍要检查流。
- 不要把异常用于普通循环分支，也不要用一个特殊整数同时表示合法值和失败。
- 本 demo 拒绝覆盖文件，但不处理多个进程同时创建同一路径，也不是数据库事务。
- 错误信息应帮助定位操作，不要输出“失败了”却不说明是参数、打开、读取还是写入。

## 三级练习

1. 预测：不给路径、给已有路径、给可创建的新路径，分别在哪个阶段结束，退出码是多少？
2. 修改：把 `firstScore(false)` 改为 true，并使用 if/else 而非 `value_or` 输出。
3. 独立：实现 `optional<int> parsePositiveInt(const string&)`，让空串、负数和非法字符返回 nullopt，并验证至少四组输入。

## 完成标准

能说明“正常缺失”和“操作失败”的区别；能在使用 optional 前检查；能从打开到关闭完整验证文件流；能让失败路径返回非 0，并解释相对路径基于哪个目录。
