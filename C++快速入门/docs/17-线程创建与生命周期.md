# 17 · 线程创建与生命周期

[返回学习地图](../README.md) · [下一篇：数据竞争与互斥锁](18-数据竞争与互斥锁.md)

## 先说结论

**真实问题：** 把工作交给另一条线程后，主线程和工作线程会同时向前运行。此时最容易出错的不是语法，而是“谁还在使用这块数据”和“谁负责等线程结束”。

**读完你能做什么：** 创建 `std::thread`、安全传值或借用参数、用 `join()` 等待结束，并识别 `detach`、悬空引用和线程异常的风险。

**为什么有用：** 后台 I/O、耗时计算和任务消费都要先解决生命周期。线程没有可靠收尾，后面的 mutex、future 和线程池都无从谈起。

## 问题一：线程创建后已经开始竞争时间

`std::thread` 构造成功后，新线程就可以立即执行。不要假设“构造语句的下一行一定先发生”。

把它想成把工作单交给同事：工作单一交出去，对方随时可能动手；你不能一边让对方填写表格，一边无保护地读写同一张表格。

传给 `std::thread` 的函数和参数默认会被复制或移动到线程内部。需要修改外部对象时，必须显式表达“借用”，并保证对象活得足够久：

```cpp
int result{0};
std::thread worker(calculate, 21, std::ref(result));
worker.join();
std::cout << result;  // join 返回后再读
```

`std::ref(result)` 不会复制 `result`，也不会延长它的生命。裸指针、引用捕获和 `this` 都有相同的借用风险。

## 方案一：让拥有者明确等待线程结束

`std::thread` 对象是线程的管理句柄，不是线程执行本身。`joinable()` 表示这个句柄仍关联着一条必须收尾的线程。即使线程函数已经运行完，只要还没有 `join` 或 `detach`，它仍可能是 joinable。

`join()` 做两件事：

1. 阻塞调用者，直到目标线程结束。
2. 建立同步关系：目标线程结束前的写入，在 `join()` 返回后可以被调用者安全观察。

这不代表 `join()` 前可以随意读共享数据。正确顺序是“工作线程写入 → 工作线程结束 → 主线程 join 返回 → 主线程读取”。

如果一个 joinable 的 `std::thread` 被析构，程序会调用 `std::terminate`，不会自动帮你 join。因此实际代码应让 RAII 对象负责收尾。第 18、21 篇的完整 demo 使用 `JoiningThreads`：无论正常离开还是线程创建中途抛异常，它都会 join 已经创建的线程。

## Java 对照：相似接口，不同的对象生命

| Java | C++17 | 需要记住的差别 |
| --- | --- | --- |
| `new Thread(task).start()` | 构造 `std::thread(task)` | 两者创建后都可能立即运行 |
| `thread.join()` | `thread.join()` | 都等待线程结束 |
| Runnable 持有 Java 对象引用 | thread 按值保存任务和参数 | `std::ref`、裸指针和引用捕获不会延长 C++ 对象生命 |
| `ExecutorService` | 第 22 篇的 `TaskExecutor` | 业务任务通常更适合交给受管理执行器 |
| 未捕获异常结束当前 Java 线程 | 异常逃出 C++ 线程入口会 `std::terminate` | 普通 `thread.join()` 不会把异常带回主线程 |

Java 的 daemon thread 和 `Thread.interrupt` 在 C++17 中没有直接对应物。C++17 通常用受 mutex 保护的状态或 atomic 标志进行协作停止；等待 condition_variable 的线程还需要收到通知。

## 为什么不把 detach 当成“后台运行”

`detach()` 只是解除 `std::thread` 对执行线程的管理。之后不能再 join，也无法从这个句柄确认任务何时完成。

这像撕掉任务回执：任务也许还在执行，但拥有者已经无法等待它。如果任务借用了局部变量或 `this`，拥有者先销毁对象就会留下悬空访问；进程退出时，分离线程也可能尚未完成。入门阶段和普通业务代码应优先 join 或使用第 22 篇那样的执行器。

## 线程函数中的异常必须有出口

异常不能直接越过线程入口：

```cpp
std::thread worker([] {
    try {
        doWork();
    } catch (const std::exception& error) {
        // 记录错误，或写入线程安全的结果通道
    }
});
```

如果需要把结果或异常交回调用线程，`std::future` 比手写共享错误变量更合适，第 20 篇会专门讲。

## 验证：运行最小 demo

完整源码：[demos/17.cpp](../demos/17.cpp)

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/17.cpp -o build/demo_17
./build/demo_17
```

预期输出：

```text
result: 42
joinable after join: false
```

对应时间线：

```text
主线程：创建 worker ───────── join 等待 ─────────► 读取 result=42
工作线程：          calculate 写 result ─► 结束
```

输出稳定的原因不是线程调度固定，而是主线程在读取 `result` 前完成了 join。

## 局限与常见坑

- 不要用 `sleep` 猜线程是否结束；时间延迟不是同步协议。
- 不要把多条线程的输出顺序当测试依据；调度顺序没有保证。
- `std::ref` 只表示借用，借用对象必须活到线程结束。
- 普通 `std::thread` 没有返回值通道，也不会通过 join 传播异常。
- `join()` 可能长时间阻塞；任务怎样停止必须另行设计。
- 不要让线程捕获即将销毁的局部引用或拥有者的裸 `this`。
- `shared_ptr` 的引用计数可以安全地由多线程增减，不代表所指对象的字段自动线程安全。
- 循环创建多条线程时，中途构造失败也必须 join 已创建线程；后续 demo 的 `JoiningThreads` 会处理这条异常路径。

## 三级练习与完成标准

1. **预测：** 把 `join()` 移到输出之后为什么不安全？只分析，不运行有数据竞争的版本。
2. **修改：** 让 worker 接收两个整数，并通过引用把它们的和写入 `result`。
3. **独立：** 启动三条线程，各自写入数组的一个独立槽位；全部 join 后由 main 按固定顺序输出。

完成标准：能解释参数为什么需要 `std::ref`、join 前后分别有什么保证、线程对象和执行线程为何不是同一个生命周期，并能保证每个 joinable thread 都被可靠收尾。
