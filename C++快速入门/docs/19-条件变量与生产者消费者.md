# 19 · 条件变量与生产者消费者

[返回学习地图](../README.md) · [下一篇：async与future](20-async与future.md)

## 先说结论

**真实问题：** 队列为空时，消费者既不能不断循环浪费 CPU，也不能只检查一次就永远睡下去；任务到达或系统关闭时，它必须可靠醒来。

**读完你能做什么：** 用 `std::condition_variable` 写出“有任务或需要停止才继续”的等待循环，正确处理虚假唤醒、通知和 drain 关闭。

**为什么有用：** 任务队列、连接池、日志线程和后台执行器都建立在同一模式上：状态由 mutex 保护，条件变量只负责等待状态变化。

## 问题：轮询浪费 CPU，单独通知又不保存事实

下面这种消费者会在空队列上持续占用 CPU：

```cpp
while (!finished) {
    if (!jobs.empty()) {
        process(jobs.front());
    }
}
```

给循环加 `sleep` 也没有解决同步：等待太短仍浪费资源，等待太长又增加延迟，而且对 `jobs` 和 `finished` 的无锁访问本身可能就是数据竞争。

生活中可以把任务队列看成取餐架，把通知看成叫号铃。铃声只提醒“情况可能变了”，真正的事实是架子上有没有餐、店铺是否打烊。错过一次铃声不会丢任务，因为任务仍在架子上；只听铃声却不检查架子也不可靠。

## 方案：锁住事实，带谓词等待

标准等待模式是：

```cpp
std::unique_lock<std::mutex> lock(mutex);
ready.wait(lock, [&] {
    return finished || !jobs.empty();
});
```

`wait` 会原子地释放 mutex 并进入等待；醒来后重新取得 mutex，再检查谓词。它需要 `unique_lock`，因为等待期间要暂时解锁，而 `lock_guard` 不提供这种操作。

谓词必须存在，原因有两个：

- 条件变量允许虚假唤醒。
- 通知可能发生在消费者真正开始等待之前。

无论因为什么醒来，消费者都重新检查受 mutex 保护的事实，因此不会在空队列上直接调用 `front()`。

等待与唤醒的关系可以压缩成：

```text
生产者：锁 → push/修改状态 → 解锁 → notify
                                      │
消费者：wait 时释放锁 ◄──────────────┘
          醒来后重新加锁 → 检查谓词 → pop → 解锁 → 处理
```

## 消费时只在锁内取任务

消费者应在锁内检查并取出任务，在锁外处理：

```cpp
ready.wait(lock, [&] { return finished || !jobs.empty(); });

if (finished && jobs.empty()) {
    break;
}

const int value = jobs.front();
jobs.pop();
lock.unlock();
process(value);
```

锁保护的是队列结构，不应覆盖耗时的 `process`。`break` 离开作用域时，`unique_lock` 也会自动解锁。

## 关闭契约：停止接收后排空队列

本篇选择 drain 语义：

1. 生产者不再添加任务。
2. 在 mutex 内把 `finished` 设为 true。
3. 唤醒等待者。
4. 消费者继续处理已有任务。
5. 只有 `finished && jobs.empty()` 时才退出。

所以等待谓词是“停止或有任务”，退出条件却是“停止且没有任务”。把这两个条件混为一谈，会在关闭时丢任务。

## notify_one 还是 notify_all

```cpp
{
    std::lock_guard<std::mutex> lock(mutex);
    jobs.push(value);
}
ready.notify_one();

{
    std::lock_guard<std::mutex> lock(mutex);
    finished = true;
}
ready.notify_all();
```

新增一个任务通常只需要一个消费者处理，所以使用 `notify_one`。全局停止会让所有等待消费者的退出条件都可能成立，因此关闭时使用 `notify_all`；否则未被唤醒的消费者可能一直等待，使 join 无法返回。

C++ 的 `notify_one/notify_all` 不要求调用时仍持有 mutex。先在锁内修改状态、解锁后再通知是常见写法，可避免刚醒来的线程立刻又被同一把锁挡住；在持锁状态下通知本身并非语言错误。

## Java 对照：Condition 和 wait/notify 的共同核心

| Java | C++17 | 需要记住的差别 |
| --- | --- | --- |
| `Condition.await()` | `condition_variable::wait(unique_lock)` | 都在等待时释放锁，返回前重新取得锁 |
| `while (!predicate) await()` | `wait(lock, predicate)` | 都必须围绕共享状态反复检查条件 |
| `signal()/signalAll()` | `notify_one()/notify_all()` | 通知只叫醒等待者，不保存业务状态 |
| `BlockingQueue` | 项目提供的并发队列或自建队列 | C++ 标准库没有直接等价的阻塞队列 |

Java 的 `Object.notify/notifyAll` 要求持有对象 monitor，`Condition.signal` 要求持有对应 `Lock`；C++ 的 notify 本身没有这项要求。两边共同的硬规则是：决定谓词结果的共享状态必须遵守同一套锁协议。

## 验证：生产五个值并排空

完整源码：[demos/19.cpp](../demos/19.cpp)

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/19.cpp -o build/demo_19
./build/demo_19
```

预期输出：

```text
sum: 15
```

producer 在锁内修改 `jobs/finished`，consumer 在锁内检查和 pop，`sum` 只由 consumer 写，main 又在 join 后读取，因此输出确定。即使 producer 在 consumer 开始等待前已经放完所有值，谓词也能直接看到队列非空。

## 局限与常见坑

- 调用 `wait(lock)` 后不检查条件，可能被虚假唤醒击穿。
- 修改 `finished` 却不通知，等待线程可能永远不醒。
- 一看到 `finished` 就退出，会丢掉队列中已接收的任务。
- 谓词读取的每项状态都应由同一 mutex 保护。
- 销毁 condition_variable、mutex 或队列前，必须让全部等待线程退出并 join。
- 多个消费者共同修改 `sum` 时，`sum` 也会成为共享状态；可使用每线程局部结果，或另行同步。
- 本 demo 只有一个生产者。多个生产者需要定义“谁有权宣布不再生产”，常见做法是由拥有者统一关闭或维护生产者计数。
- 队列没有容量上限；真实服务还要考虑生产快于消费时的背压策略。

## 三级练习与完成标准

1. **预测：** producer 在 consumer 等待前已经放完所有值，为什么程序仍不会丢通知或卡住？
2. **修改：** 让消费者同时统计数量和总和，join 后固定输出 `count: 5, sum: 15`。
3. **独立：** 增加第二个消费者。每个消费者只写自己的局部结果，最后由 main 合并；不要断言某个消费者一定拿到某个任务。

完成标准：能写出带谓词的 wait，让谓词状态遵守同一把 mutex 的协议；能解释新增任务为什么用 notify_one、关闭为什么用 notify_all，以及 drain 模式为什么要在队列为空后才退出。
