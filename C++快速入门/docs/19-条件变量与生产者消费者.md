# 19 · 条件变量与生产者消费者

[返回学习地图](../README.md) · [下一篇：async与future](20-async与future.md)

## 本篇目标

使用 `std::condition_variable` 在“有任务或停止”时唤醒消费者，理解谓词、虚假唤醒、停止协议和锁外处理。

## 学习作用

消费者在队列为空时若持续循环检查，会浪费 CPU。条件变量让线程睡眠，并在共享状态可能满足条件时重新检查，是任务队列、连接池和后台工作线程的核心构件。

## Java 对照

Java 的 `wait/notify` 或 `Condition.await/signal` 与 C++ condition_variable 思路接近：状态由锁保护，等待必须放在循环/谓词中。Java 实际业务通常优先 BlockingQueue；C++ 项目也应优先使用成熟队列或执行器，而不是每个功能都手写条件变量。

Java 的 Object.notify/notifyAll 要求持有对象 monitor，Condition.signal 要求持有对应 Lock；C++ 的 notify_one/notify_all 本身不要求调用者正持有 mutex，所以本篇 demo 在解锁后通知是正确的。两边真正必须遵守的共同规则是：决定谓词结果的共享状态要按同一套锁协议访问。

通知本身不是可以积攒的“任务许可证”。真正的事实保存在受 mutex 保护的 jobs 和 finished 中，通知只负责叫醒等待者重新检查事实。

## 标准等待模式

```cpp
std::unique_lock<std::mutex> lock(mutex);
ready.wait(lock, [&] { return finished || !jobs.empty(); });
```

condition_variable 使用 unique_lock，因为 wait 需要原子地释放 mutex、进入等待，并在醒来后重新取得 mutex。谓词可能执行很多次；它只读取受同一把锁保护的状态。

必须使用谓词，因为线程可能虚假唤醒，也可能在真正开始等待前已有通知。醒来后直接 `jobs.front()` 会在空队列上出错。

停止语义需要提前定义。本 demo 选择 drain：finished 为 true 后不再生产，但消费者仍处理队列中已有任务；只有 `finished && jobs.empty()` 才退出。

新增一个任务通常只需要一个消费者处理，所以 push 后使用 notify_one。全局停止会让所有等待消费者的退出条件都可能成立，因此关闭时使用 notify_all；否则没被叫醒的消费者可能一直等待，导致 join 无法返回。

## 可运行 demo

源码：[demos/19.cpp](../demos/19.cpp)：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/19.cpp -o build/demo_19
./build/demo_19
```

```cpp
#include <condition_variable>
#include <iostream>
#include <mutex>
#include <queue>
#include <thread>

int main() {
    std::queue<int> jobs;
    std::mutex mutex;
    std::condition_variable ready;
    bool finished{false};
    int sum{0};

    std::thread producer([&] {
        for (int value{1}; value <= 5; ++value) {
            {
                std::lock_guard<std::mutex> lock(mutex);
                jobs.push(value);
            }
            ready.notify_one();
        }
        {
            std::lock_guard<std::mutex> lock(mutex);
            finished = true;
        }
        ready.notify_all();
    });

    std::thread consumer([&] {
        while (true) {
            std::unique_lock<std::mutex> lock(mutex);
            ready.wait(lock, [&] { return finished || !jobs.empty(); });
            if (jobs.empty() && finished) break;
            const int value = jobs.front();
            jobs.pop();
            lock.unlock();
            sum += value;
        }
    });

    producer.join();
    consumer.join();
    std::cout << "sum: " << sum << '\n';
}
```

预期输出：

```text
sum: 15
```

producer 在锁内修改 jobs/finished，解锁后通知。consumer 在锁内等待、检查并取出一个值，然后显式 unlock，避免处理任务时占着队列锁。sum 只由 consumer 写，main 在 join 后读，所以无需另一把锁。

## 常见坑

- `wait(lock)` 后不检查条件，可能被虚假唤醒击穿。
- 改 finished 却不通知，消费者可能永远睡眠。
- 一看到 finished 就退出，会丢掉队列里尚未处理的任务。
- 多个消费者时，当前 demo 的 sum 会变成共享写入，需要每线程局部和、mutex 或 atomic。
- 销毁 condition_variable、mutex 或队列前，必须保证所有等待线程已经结束并 join。

## 三级练习与完成标准

1. 预测：producer 在 consumer 开始等待前已经放完所有值，谓词为什么仍能正常工作？
2. 修改：让消费者统计处理数量和总和，join 后固定输出 `count: 5, sum: 15`。
3. 独立：增加第二个消费者，每个消费者只写自己的局部结果，最后由 main 合并，输出不依赖谁处理了哪个任务。

完成标准：能写出带谓词的 wait，所有谓词状态由同一 mutex 保护，停止时 notify_all，并在退出前排空或按明确约定丢弃队列。
