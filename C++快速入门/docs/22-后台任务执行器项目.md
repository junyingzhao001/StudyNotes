# 22 · 后台任务执行器项目

[返回学习地图](../README.md) · [返回线程起点](17-线程创建与生命周期.md)

## 本篇目标

把 thread、mutex、condition_variable、packaged_task 和 future 组合成一个单工作线程任务执行器，并通过确定性测试验证生命周期、FIFO、异常与停止语义。

## 学习作用

真实业务代码通常不希望每次都手写 thread 和 join，而是把任务交给长期存在的执行器。这个项目规模小，但已经包含线程组件最重要的设计问题：共享状态由谁拥有、何时停止、队列是否排空、异常如何返回、析构是否等待。

## 第一遍只抓住调用主线

第一次学习不要求默写整个类。先做到三件事：画出 submit → queue → worker → packaged_task → future 的路径；解释队列为什么要加锁、worker 为什么要带谓词等待；能按值捕获参数并从 future 取得值或异常。

`invoke_result_t`、用 shared_ptr 适配 C++17 std::function，以及后面的 thread_local 和双 mutex，都是为了让接口更通用、让关闭边界更牢固的工程实现。第一遍知道它们各自解决什么问题即可，第二遍再对照源码复现。这样不会让模板细节盖过线程主线。

## 五条不变量

1. tasks_ 与 stopping_ 每次访问都由同一把 mutex_ 保护。
2. submit 成功返回 future 的任务一定会执行；shutdown 后的新任务被拒绝。
3. 工作线程只在锁内取任务，在锁外执行任务，长任务不会阻塞 submit。
4. shutdown 采用 drain 语义：先停止接收，执行完已入队任务，再 join。
5. TaskExecutor 不能复制或移动，因为 worker_ 持有 this 并持续访问成员。

## 并发 API 契约

- 多个生产者线程可以同时调用 submit，队列锁会串行修改 tasks_。
- submit 与 shutdown 可以竞争；谁先在 mutex_ 保护下处理 stopping_，决定该任务被接收还是被拒绝。
- 只要 submit 成功返回 future，该任务就属于已接收任务，shutdown 必须把它执行完。
- 多个外部线程可以同时调用 shutdown，调用都会等到同一 worker 完成；重复调用也安全。
- 析构开始后，任何线程都不能再调用该对象的成员函数。mutex 能同步成员状态，不能延长 C++ 对象生命周期。

不要在业务代码中先“检查是否关闭”再决定 submit；检查与提交之间状态仍可能变化。直接调用 submit，并在调用边界处理“执行器正在关闭”的异常。

## submit 如何返回 future

submit 接收一个无参数可调用对象。若任务需要参数，用 Lambda 按值捕获：

```cpp
int left{20};
int right{22};
auto result = executor.submit([left, right] { return left + right; });
```

内部把 Lambda 放进 `std::packaged_task<Result()>`，先取得 future，再把执行 packaged_task 的小函数放入队列。任务返回值或异常都会进入 future 的共享状态。

packaged_task 只能移动，而 C++17 `std::function` 要求保存的可调用对象可复制，因此代码用 shared_ptr 拥有 packaged_task，再把这个可复制的 shared_ptr 捕获进队列 Lambda。这里 shared_ptr 解决的是队列类型约束，不表示所有业务对象都应共享所有权。

submit 是函数模板，所以定义放在头文件，让每个调用它的编译单元都能看到完整定义。返回类型使用 `invoke_result_t` 在编译期推导任务结果类型。

## 工作循环与停止

```text
submit 线程：创建 packaged_task → 锁队列 → push → 解锁 → notify
                                          │
工作线程：wait(predicate) ◄───────────────┘
          锁内 pop → 解锁 → 执行 task → 值/异常进入 future

shutdown：设置 stopping → notify_all → worker 排空队列 → join 返回
```

condition_variable 的谓词是 `stopping_ || !tasks_.empty()`。醒来后只有在 stopping 且队列为空时退出，所以不会丢掉已经接受的任务。

下面属于第二遍的关闭加固。shutdownMutex_ 让多个外部线程不能同时 join 同一个 worker，重复 shutdown 也安全。

`thread_local` 表示每条线程各自拥有一份变量：worker 进入 run 时把自己正在执行的 TaskExecutor 地址写入本线程的那一份，退出前清空；外部线程看到的是各自独立的值，所以这里不需要 mutex。shutdown 必须在取得 shutdownMutex_ 之前检查当前线程的标记，否则外部线程可能持锁等待 worker，而 worker 又等待同一把锁，形成死锁。工作线程里的任务调用自己的 executor.shutdown 时会抛 logic_error；若执行器本身在工作线程中析构，析构无法安全恢复，会终止程序。因此执行器必须由工作线程之外的、更长生命周期对象拥有。

## 编译运行

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread -Iconcurrency \
  concurrency/main.cpp concurrency/task_executor.cpp \
  -o build/task_executor_demo
./build/task_executor_demo
```

预期输出：

```text
square: 144
error: task failed
```

任务异常不会逃出工作循环，而是在 future.get 时由主线程接收。一个异常任务之后，执行器仍能继续处理下一项。

## 必须知道的边界

- 析构会等待所有已接收任务完成；若任务永久阻塞，析构也会永久等待。C++17 没有安全强杀线程的通用办法。
- 单工作线程的任务若 submit 新任务后立刻对新 future 调用 get，会死锁：唯一 worker 正被当前任务占用。
- Lambda 按引用捕获的对象可能在任务执行前已经销毁；默认优先按值捕获，或使用有明确生命期的共享状态。
- packaged_task 会把任务异常保存进 future，不会自动写日志；调用者若直接丢弃 future，这个异常可能无人观察。需要结果的任务应保留并 get；确实无需结果的业务任务应使用项目统一的日志/错误包装。
- 不要让队列任务持有执行器的最后一个 owning shared_ptr，否则最后一个任务可能在 worker 上触发执行器析构。
- 当前项目没有取消、优先级、限长队列或多个 worker，这些都需要重新定义接口与停止语义。
- 不要在其他线程仍调用 submit 时直接销毁 executor；mutex 能协调操作状态，但不能让已经开始析构的 C++ 对象继续合法存在。

## 三级练习与完成标准

1. 预测：依次提交 A、B、C 后立即 shutdown，为什么三项仍都会执行？
2. 修改：增加线程安全的 pending()，先定义它统计“仅排队任务”还是“排队 + 正在执行”。
3. 独立：先写一个只接收 `std::function<int()>`、只由 main 调用 shutdown 的简化版单 worker 执行器；通过后再与完整实现比较。多 worker、取消和限长队列留作进阶项目。

第一遍完成标准：能画出完整调用路径，解释 future 如何收到异常、为什么执行任务前要解锁、析构为何可能阻塞，并能修改任务和测试。第二遍再要求解释五条不变量、自关闭检查为何在 shutdownMutex_ 之前，以及哪些捕获会造成悬空。达到这里即可在有代码评审和测试的前提下处理小型项目中的常见后台任务需求。
