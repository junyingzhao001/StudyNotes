# 22 · 后台任务执行器项目

[返回学习地图](../README.md) · [返回线程起点](17-线程创建与生命周期.md)

## 先说结论

**真实问题：** 业务代码若为每个后台任务临时创建线程，就很难统一限制执行顺序、返回结果、传播异常并安全关闭。

**读完你能做什么：** 读懂并修改一个 C++17 单工作线程执行器；它支持多生产者 `submit`、返回 `future`、传播任务异常，并在 `shutdown` 或析构时排空已接收任务后 join。

**为什么有用：** 这个项目把前五篇的 thread、mutex、condition_variable、future 和 atomic 思维连接成一个真实组件。它也是阅读线程池、事件循环和异步框架的最小模型。

## 问题：创建线程容易，管理任务系统很难

直接为每项工作创建 `std::thread` 会把这些问题散落到业务代码：

- 任务如何排队，是否保持顺序？
- 多个调用者能否同时提交？
- 返回值和异常交给谁？
- 关闭后是否继续接收任务？
- 已经接收的任务是完成还是丢弃？
- 谁负责让工作线程停止并 join？

本项目只使用一个 worker，把重点放在协议正确性。它的目标是教学和小型任务串行化，不是替代生产环境的成熟线程池。

## 生活类比：单窗口服务台

可以把执行器看成只有一个办事窗口的服务台：

- 多个顾客是并发调用 `submit` 的生产者。
- 任务队列是取号后的等候队列。
- worker 是唯一的窗口工作人员。
- future 是回执，最终保存办理结果或失败原因。
- condition_variable 是叫醒正在休息的工作人员的铃。
- `shutdown` 是挂出“停止取号”牌：已取号的人继续办完，新顾客被拒绝。

这个类比对应本项目的 drain 语义。窗口工作人员不能调用 shutdown 后再等待自己下班，否则会等待自己结束。

## Java 对照

| C++ 项目类型 | Java 中接近的概念 | 关键差别 |
| --- | --- | --- |
| `TaskExecutor` | `Executors.newSingleThreadExecutor()` | 本项目是用于学习协议的最小实现 |
| `queue<function<void()>>` | `BlockingQueue<Runnable>` | C++ 标准库没有直接提供 BlockingQueue |
| `packaged_task<Result()>` | `FutureTask<Result>` | 都把可执行任务连接到结果状态 |
| `future<Result>` | `Future<Result>` | C++ `get()` 直接重抛原任务异常 |
| mutex + condition_variable | `Lock + Condition` | 谓词状态必须由同一把锁保护 |
| shutdown + join | `shutdown() + awaitTermination()` | C++ 析构还必须保证 thread 不以 joinable 状态销毁 |

第一次阅读先抓住主线，不必立即默写模板：

```text
生产者线程
    │ submit(callable)
    ▼
packaged_task ───────► future 回执交给调用者
    │
    ▼
[ mutex 保护的 FIFO 队列 ] ── notify_one ──► worker
                                              │
                                     wait → pop → 解锁
                                              │
                                              ▼
                                      执行 packaged_task
                                              │
                              值或异常写回 future 共享状态
```

## 方案一：先定义五条不变量

代码正确与否，先用不变量检查：

1. `tasks_` 和 `stopping_` 的每次访问都由同一个 `mutex_` 保护。
2. `submit` 成功返回 future 的任务一定属于已接收任务；shutdown 后的新任务被拒绝。
3. worker 只在锁内取任务，在锁外执行任务。
4. shutdown 采用 drain 语义：停止接收，排空队列，再 join。
5. `TaskExecutor` 不能复制或移动，因为 worker 持续通过 `this` 访问成员。

mutex 保护的不只是 queue 本身，还保护“检查 stopping 与入队必须不可分割”这条业务规则。

## 方案二：submit 把任务和 future 接起来

调用者提交无参数可调用对象；有参数时用 Lambda 按值捕获：

```cpp
int left{20};
int right{22};
auto result = executor.submit([left, right] {
    return left + right;
});
```

`submit` 的关键路径如下，完整模板见 [task_executor.h](../concurrency/task_executor.h)：

```cpp
auto task = std::make_shared<std::packaged_task<Result()>>(
    std::forward<Function>(function)
);
auto result = task->get_future();

{
    std::lock_guard<std::mutex> lock(mutex_);
    if (stopping_) {
        throw std::runtime_error("executor is stopping");
    }
    tasks_.push([task] { (*task)(); });
}
ready_.notify_one();
return result;
```

先在同一个锁内检查 `stopping_` 再入队，消除了“刚检查完还在运行，shutdown 就插进来”的窗口。

`std::packaged_task` 只能移动，而 C++17 `std::function` 保存的可调用对象必须可复制。因此队列 Lambda 捕获一个可复制的 `shared_ptr`，由它拥有 packaged_task。这里的 shared_ptr 是类型适配手段，不表示业务对象都应该共享所有权。

`submit` 是函数模板，定义必须留在头文件中，让使用它的编译单元看到完整定义。`invoke_result_t` 只负责在编译期推导任务返回类型，第一次阅读知道这一点即可。

## 方案三：worker 用谓词等待，在锁外执行

完整循环见 [task_executor.cpp](../concurrency/task_executor.cpp)，决定正确性的部分是：

```cpp
ready_.wait(lock, [this] {
    return stopping_ || !tasks_.empty();
});

if (stopping_ && tasks_.empty()) {
    return;
}

task = std::move(tasks_.front());
tasks_.pop();
// 离开锁作用域后才调用 task()
```

等待谓词是“正在关闭或队列非空”。退出条件是“正在关闭且队列为空”。所以 shutdown 已经开始时，worker 仍会逐项处理已接收任务。

任务必须在锁外执行。否则一个慢任务会一直占有队列锁，生产者无法 submit，shutdown 也无法修改停止状态；未知任务甚至可能再次进入执行器，造成死锁。

## 方案四：明确并发 API 契约

- 多个生产者线程可以同时调用 `submit`，队列锁会串行修改共享状态。
- `submit` 与 `shutdown` 可以竞争；谁先在 `mutex_` 保护下完成“入队”或“设置 stopping”，决定任务被接收还是拒绝。
- 只要 `submit` 成功返回 future，shutdown 就必须执行该任务。
- 多个外部线程可以同时调用 `shutdown`；它们都会等到同一个 worker 完成，重复调用也安全。
- 析构开始后，任何线程都不能再调用该对象的成员。mutex 同步状态，但不会延长对象生命周期。

不要先调用“是否关闭”的查询再决定是否 submit。检查和提交之间状态仍可变化。直接调用 `submit`，并在调用边界处理“执行器正在关闭”的异常。

## 方案五：shutdown 先关门，再排队办完

关闭过程可以画成：

```text
RUNNING
  │ 在 mutex 内设置 stopping = true
  ├──────── 新 submit：抛异常
  ▼
DRAINING ── worker 继续执行队列任务 ──► 队列为空
  │
  ▼
worker 退出 ── shutdown 调用 join ──► STOPPED
```

`shutdownMutex_` 让多个外部线程不会同时对同一个 `worker_` 调用 join。持有它的调用者可以等待 worker；其他关闭调用者先等待这把关闭锁，之后看到 thread 已经不再 joinable。

## 自己关闭自己为什么需要特殊处理

[task_executor.cpp](../concurrency/task_executor.cpp) 使用 `thread_local` 标记当前线程正在运行哪个执行器。`thread_local` 表示每条线程各自有一份变量：worker 进入 `run` 时写入自己的执行器地址，退出前清空。外部线程读取的是各自独立的副本，因此这个标记不需要 mutex。

`shutdown` 必须在取得 `shutdownMutex_` **之前**检查该标记：

```cpp
if (runningExecutor == this) {
    throw std::logic_error("executor cannot stop itself");
}
```

假设外部线程已经持有 `shutdownMutex_` 并在 `join` worker；worker 内的任务若再等待这把锁，双方会互相等待。提前检查会让任务得到 `logic_error`，执行器继续运行，由外部拥有者负责关闭。

如果执行器本身在 worker 上析构，析构函数无法安全返回：它既不能 join 当前线程，也不能让成员先销毁而 worker 继续访问。因此实现选择 `std::terminate`。执行器必须由 worker 之外、生命更长的对象拥有。

## 验证一：运行结果与异常 demo

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread -Iconcurrency \
  concurrency/main.cpp concurrency/task_executor.cpp \
  -o build/task_executor_demo
./build/task_executor_demo
```

预期输出：

```text
square: 144
error: task failed
```

任务异常由 packaged_task 保存，到调用者执行 `future.get()` 时重新抛出。异常任务不会让 worker 退出，后续任务仍可运行。

## 局限与常见坑

- 析构会等待所有已接收任务完成；若任务永久阻塞，析构也会永久等待。C++17 没有安全强杀线程的通用办法。
- 单 worker 的任务若 submit 新任务后立即对新 future 调用 `get()`，会等待排在自己后面的任务，而唯一 worker 仍被当前任务占用，形成死锁。
- Lambda 按引用捕获的对象可能在任务执行前已经销毁；默认优先按值捕获，或使用生命期明确的共享状态。
- packaged_task 只把异常保存进 future，不会自动写日志。调用者若丢弃 future，异常可能无人观察；需要结果的任务应保留并 `get()`，无需结果的业务任务应使用项目统一的日志和错误包装。
- 不要让队列任务持有执行器的最后一个 owning `shared_ptr`，否则最后一个任务结束时可能在 worker 上触发执行器析构。
- 不要在其他线程仍调用 `submit` 时销毁 executor。对象开始析构后，并发成员调用属于生命周期错误。
- 当前实现没有取消、优先级、限长队列、背压或多个 worker。增加任何一项都要重新定义接口、顺序和关闭语义。
- 这是单 worker 队列，长任务会推迟后续所有任务；它没有延迟保证。

## 三级练习与完成标准

1. **预测：** 依次提交 A、B、C 后立即 shutdown，为什么三项仍会执行？指出等待谓词和退出条件分别是什么。
2. **修改：** 增加线程安全的 `pending()`。先明确它统计“仅排队任务”还是“排队任务加正在执行任务”，再写测试。
3. **独立：** 先从零写一个只接收 `std::function<int()>`、只由 main 调用 shutdown 的简化版单 worker 执行器；通过后再与完整实现比较。多 worker、取消和限长队列留作进阶项目。

第一遍完成标准：能画出 `submit → queue → worker → future` 路径，解释为什么队列要加锁、任务要在锁外运行、析构可能阻塞，并能修改 demo 和测试。

第二遍完成标准：能逐条解释五个不变量、并发 submit/shutdown 的接受边界、自关闭检查为何在 `shutdownMutex_` 之前，以及哪些捕获会悬空。
