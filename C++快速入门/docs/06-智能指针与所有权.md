# 06 · 智能指针与所有权

[返回学习地图](../README.md) · [上一篇：类、对象与 RAII](05-类对象与RAII.md) · [下一篇：string 与 STL 容器](07-string与STL容器.md)

## 先说结论

当对象需要动态生命周期时，优先用智能指针表达“谁负责让它存活、谁最终销毁它”。本篇的主角 `std::unique_ptr<T>` 表示唯一所有者；所有者析构时，它拥有的对象也会自动释放。

读完本篇，你能创建、转移和借用一个动态 `Task`，看懂 `make_unique`、`move` 和 `get`，并判断何时才需要 `shared_ptr`。这能避免手写 `new/delete` 时常见的泄漏、重复释放和所有权不清。

## 问题：Java 引用没有直接表达“唯一所有者”

Java 由 GC 跟踪对象是否仍可达，普通对象变量通常不说明谁负责销毁对象。C++ 需要更明确地区分：

- 直接拥有一个局部值；
- 临时借用别人的对象；
- 唯一拥有一个动态对象；
- 多个所有者共同维持动态对象的生命。

如果 `Task` 只在当前作用域使用，最简单的写法仍是局部对象 `Task task{...};`。只有生命周期、运行时多态或数据结构确实需要动态分配时，才需要智能指针。

## 方案：用 unique_ptr 表达唯一所有权

关键代码来自完整的 [demos/06.cpp](../demos/06.cpp)：

```cpp
auto owner = std::make_unique<Task>("Learn ownership");
printTask(owner.get());              // 移动前使用
Task* borrowed = owner.get();        // 只借用，不取得所有权
auto nextOwner = std::move(owner);   // 转移唯一所有权
printTask(borrowed);
```

按顺序理解这四步：

1. `make_unique<Task>(...)` 创建 Task，并返回唯一拥有它的 `unique_ptr<Task>`。
2. `owner.get()` 得到原始指针，只用于借用同一个 Task。
3. `std::move(owner)` 允许把所有权交给 `nextOwner`。
4. 对 unique_ptr 而言，移动完成后 `owner == nullptr`；Task 没有被复制，仍是同一个对象。

`std::move` 本身只是把表达式转换为“允许被移动”的形式，真正的转移动作由目标类型完成。第 09 篇会继续解释普通对象的移动规则；本篇只记住 unique_ptr 不能复制，转移时要明确写 move。

## 所有权变化要能画出来

| 时刻 | owner | nextOwner | borrowed | Task 是否存活 |
| --- | --- | --- | --- | --- |
| make_unique 后 | 拥有 Task | 尚未创建 | 指向 Task | 是 |
| move 后 | 空 | 拥有同一个 Task | 仍指向同一 Task | 是 |
| nextOwner 析构或 reset 后 | 空 | 不再拥有 | 悬空，不能使用 | 否 |

移动 unique_ptr 只更换所有者，不会因此搬动它管理的 Task。所以 `borrowed` 在 `nextOwner` 继续拥有 Task 时仍有效；所有者释放 Task 后，borrowed 才失效。

## 按意图选择类型

| 关系 | 推荐写法 | Java 中较接近的理解 |
| --- | --- | --- |
| 当前作用域直接拥有 | `T value` | 创建普通对象，但 C++ 销毁时机由作用域决定 |
| 一定存在的只读借用 | `const T&` | 非 null、只读使用 |
| 一定存在的修改借用 | `T&` | 修改传入对象 |
| 可空借用 | `T*` / `const T*` | 可为 null 的对象引用，但不会延长生命 |
| 动态对象只有一个所有者 | `std::unique_ptr<T>` | Java 没有直接对应类型 |
| 确有多个独立所有者 | `std::shared_ptr<T>` | 多个强引用共同维持对象可达 |
| 观察 shared_ptr 对象但不参与拥有 | `std::weak_ptr<T>` | 类似不阻止回收的弱引用 |

`shared_ptr` 通过引用计数管理共享生命期，但不应作为默认选择。两个 shared_ptr 相互拥有会形成循环，通常需要把其中一条关系改为 weak_ptr。引用计数可并发变化，也不代表 Task 自身的字段自动线程安全。

## 验证：移动后旧所有者为空

在 `C++快速入门` 目录执行：

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g demos/06.cpp -o build/demo_06
./build/demo_06
```

预期输出：

```text
Learn ownership
old owner empty: true
Learn ownership
```

第一行来自移动前的访问；第二行确认 owner 已为空；第三行通过 borrowed 再次访问同一个 Task，说明 nextOwner 仍拥有它并让它存活。

## 常见坑

- 不要复制 unique_ptr；需要交接所有权时使用 `std::move`。
- 移动后的 owner 可以析构、重新赋值或判断是否为空，但不能当作仍拥有原对象。
- `get()` 不转移所有权。不要把结果交给另一个智能指针重新拥有，也不要手动 delete。
- `p->field` 等价于 `(*p).field`；访问前仍要确认指针有效。
- 不要让借用指针或引用活得比最后一个所有者更久。
- 多个代码位置需要访问同一对象，不一定代表需要 shared_ptr；若一个位置拥有、其他位置短暂借用，unique_ptr 仍可能更合适。

## 三级练习

1. **预测**：移动后，分别把 `owner.get()` 和 `nextOwner.get()` 传给能处理空指针的 `printTask`，会输出什么？
2. **修改**：实现 `std::unique_ptr<Task> makeTask(const std::string& title)`，从函数返回所有者。
3. **独立完成**：实现 `consumeTask(std::unique_ptr<Task> task)` 表达接管所有权；从 main 用 move 调用，并说明调用后原 owner 的状态。

## 完成标准

能为动态 Task 标出唯一所有者、每个借用者和销毁时刻；能解释 make_unique、move、get 各自是否改变所有权；不会把 shared_ptr 当成 Java 普通引用的机械替代。

## 马上动手

1. 运行 demo，核对移动前后的三行输出。
2. 在纸上画出 move 前后的 owner、nextOwner 和 borrowed，标出谁拥有 Task、谁只是在借用。
3. 暂时把最后一行改成 `printTask(owner.get())`；运行后第三行会消失，因为旧 owner 已为空。
4. 恢复为 `printTask(borrowed)`，确认第三行回来；再说明为什么 nextOwner 析构或 reset 后不能继续解引用 borrowed。
