# 10 · 模板与运行时多态

[返回学习地图](../README.md) · [下一篇：错误处理与文件读写](11-错误处理与文件读写.md)

## 先说结论

这一篇解决两类“同一套接口处理不同类型”的问题：类型在编译时已经确定时使用模板；只知道统一接口、实际对象到运行时才确定时使用虚函数。

读完后，你能看懂 `vector<int>` 背后的模板思路，也能读懂 `unique_ptr<Shape>` 为什么会调用 `Rectangle::area()`。这两种机制都常被称为多态，但选择时机不同。

## 问题：同一套接口面对两种“类型何时确定”

“处理不同类型”至少包含两种需求：调用处可能在编译时就知道具体类型，也可能只知道统一接口，要到运行时才拿到实际对象。前一种更适合模板，后一种更适合虚函数。若不先分清决定时机，很容易为了复用几行代码建立不必要的继承，或在需要运行时替换对象时误用模板。

## 方案一：类型在编译时确定，用模板

“返回两个值中较大的一个”对 int、double 等类型逻辑相同。为每种类型复制一份函数会产生重复代码。

方案是函数模板：

```cpp
template<typename T>
T larger(T left, T right) {
    return left > right ? left : right;
}
```

调用 `larger(3, 7)` 时，编译器推导 `T = int`，并检查 int 是否支持 `>`。模板定义通常放在头文件中，因为使用它的编译单元需要看到完整定义才能实例化。

Java 泛型常通过类型擦除工作，基本类型通常需要装箱；C++ 模板会针对实际类型实例化，`vector<int>` 可以直接存 int。模板报错较长时，从第一条落在自己代码的诊断开始，先核对传入的实际类型。

## 方案二：对象在运行时确定，用虚函数

绘图代码只想依赖 `Shape::area()`，实际对象可能是 Rectangle、Circle 或 Square。对象类型要到运行时才知道，此时需要虚函数分派。

[完整 demo](../demos/10.cpp) 中的关键关系是：

```cpp
class Shape {
public:
    virtual ~Shape() = default;
    virtual double area() const = 0;
};

std::unique_ptr<Shape> shape =
    std::make_unique<Rectangle>(3.0, 4.0);
std::cout << shape->area() << '\n';
```

`= 0` 表示纯虚函数，因此 Shape 是抽象类，不能直接实例化。shape 的静态类型是 `unique_ptr<Shape>`，实际对象是 Rectangle；调用 virtual 方法时，运行期选择 `Rectangle::area()`。

通过基类指针销毁派生对象时，基类需要虚析构函数。派生类的方法应写 `override`，让编译器检查参数、返回类型和尾部 `const` 是否真的覆盖基类声明。

## Java 对照：相似处与差别

| 需求 | Java 常见做法 | C++ 做法 |
| --- | --- | --- |
| 编译期复用类型逻辑 | 泛型 `<T>` | `template<typename T>` |
| 通过接口调用实际实现 | interface/abstract class | virtual / 纯虚函数 |
| 检查方法覆盖 | `@Override` | `override` |
| 管理多态对象生命 | GC 引用 | 常用 `unique_ptr<Base>` |

Java 普通实例方法通常动态分派；C++ 只有基类中声明为 `virtual` 的方法才参与虚分派。C++ 还要避免按值复制派生对象到基类对象，因为这会发生对象切片，丢失派生部分。

## 验证：观察两个决定时机

在课程目录执行：

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g demos/10.cpp -o build/demo_10
./build/demo_10
```

预期输出：

```text
larger: 7
area: 12
```

第一行在编译期确定 `T = int`；第二行在运行期根据 Rectangle 对象进入对应实现。

## 怎么选择

- 调用处知道具体类型，要求类型支持某些操作：优先考虑模板。
- 调用处只依赖稳定接口，需要在运行时替换实现：考虑虚函数接口。
- 只是把数据和几个行为组合起来：普通类或组合往往已经足够，不必为了“面向对象”强行继承。

## 局限与常见坑

- `larger(3, 4.5)` 无法为同一个 `T` 直接推导出一致类型；可统一实参类型或显式写 `larger<double>(3, 4.5)`。
- 派生类漏写尾部 `const` 时，`override` 会报告没有覆盖；不要删掉 override 来掩盖问题。
- 基类析构函数非虚，却通过基类指针销毁派生对象，会产生未定义行为。
- 在可实例化的基类层次中，`Base sliced = derived` 会切掉派生部分；本例 Shape 是抽象类，直接按值创建 Shape 会编译失败。多态对象通常通过引用或智能指针使用。
- 模板与继承都会增加接口复杂度，只在它们解决真实变化点时使用。

## 完成标准

能说出模板在编译期适配类型、虚函数在运行期选择实现；能解释纯虚函数、override、虚析构和对象切片；能根据变化发生的时机选择机制。
