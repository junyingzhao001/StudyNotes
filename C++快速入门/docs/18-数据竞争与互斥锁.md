# 18 · 数据竞争与互斥锁

[返回学习地图](../README.md) · [下一篇：条件变量与生产者消费者](19-条件变量与生产者消费者.md)

## 先说结论

**真实问题：** 两条线程无同步地访问同一内存位置，只要至少一方写入，程序就可能发生数据竞争。它不是“偶尔少算一次”，而是未定义行为。

**读完你能做什么：** 用 `std::mutex` 和 RAII 锁保护共享状态，判断锁应该覆盖哪些操作，并识别无锁读取、锁范围过大和多锁死锁。

**为什么有用：** 容器、缓存、账户状态和任务队列通常包含多步业务规则。mutex 保护的是这套规则，而不只是某一个变量。

## 问题：`++counter` 不是一个不可分割动作

普通整数的递增通常包含“读取 → 加一 → 写回”。两条线程交错执行时，可能都读到旧值，再互相覆盖结果。

更关键的是，C++ 对数据竞争的定义比“结果不准”严格：对同一内存位置发生无同步的冲突访问，其中至少一个是写入且访问不是原子操作，程序就进入未定义行为。编译器无需保留你凭直觉推测的执行顺序。

“同一内存位置”比“同一个对象”更精确。同一 struct 的两个独立普通成员通常位于不同内存位置，不会只因属于同一对象就自动产生数据竞争；但如果它们共同组成“余额和流水号必须一致”这样的业务不变量，仍应遵守同一个锁协议。对 `vector` 做 `push_back`、`erase` 等结构修改时，也不能同时无锁读取该容器。

把共享状态想成一本多人使用的账本：mutex 是账本唯一的钥匙。拿到钥匙的人应完成一整笔必须一致的修改，而不是只锁住其中一行。

## 方案：用 mutex 定义唯一访问协议

`std::lock_guard` 在构造时加锁，离开作用域时自动解锁：

```cpp
void increment(int& counter, std::mutex& mutex) {
    std::lock_guard<std::mutex> lock(mutex);
    ++counter;
}
```

异常或提前 `return` 都不会跳过解锁。相比手写 `mutex.lock()` 和 `mutex.unlock()`，这种 RAII 写法更不容易遗漏清理。

同一共享状态的**所有并发访问**都必须遵守同一协议。只给写入加锁而读取不加锁仍可能有数据竞争；`const` 只限制当前接口的修改能力，也不自动提供线程安全。

## Java 对照：mutex 更像显式的 synchronized

| Java | C++17 | 需要记住的差别 |
| --- | --- | --- |
| `synchronized` | `mutex + lock_guard` | lock_guard 用作用域保证解锁 |
| `ReentrantLock` + `try/finally` | `mutex + lock_guard/unique_lock` | `std::mutex` 不可重入，同一线程重复锁它会出问题 |
| 并发集合 | 项目提供的并发容器或自行封装锁 | `vector/map` 不会自动变成线程安全 |
| Java `volatile` | 没有可直接照搬的 C++ `volatile` 用法 | C++ `volatile` 不能修复数据竞争；简单原子值见第 21 篇 |

和 Java 一样，锁对象本身不是业务状态。关键是团队约定“访问这些字段必须先取得哪把锁”，并把状态和 mutex 封装在同一个类中，避免调用者绕过协议。

## 锁多大范围才合适

锁的范围必须覆盖完整不变量。例如“检查余额足够，再扣款”要在同一个临界区内完成，不能分别加锁：

```cpp
{
    std::lock_guard<std::mutex> lock(accountMutex);
    if (balance >= amount) {
        balance -= amount;
        lastTransactionId = id;
    }
}
```

同时也不要在持锁时执行耗时 I/O、`sleep`、未知回调、`join()` 或 `future.get()`。这些操作可能很慢，也可能反过来等待同一把锁。

需要同时取得两把 mutex 时，线程 A 按 `m1 → m2`、线程 B 按 `m2 → m1` 会互相等待。C++17 可用：

```cpp
std::scoped_lock lock(m1, m2);
```

它能以避免死锁的方式取得多把锁。真实项目还应保持清楚、统一的锁顺序，减少多锁设计。

## RAII 也要负责线程本身

本篇完整 demo 使用 `JoiningThreads` 管理 `vector<thread>`：

```cpp
{
    std::vector<std::thread> workers;
    JoiningThreads joining{workers};
    // 创建线程；离开作用域时 joining 先析构并 join 全部线程
}
std::cout << counter;
```

`joining` 比 `workers` 后构造，因此会先析构。即使循环中某次线程创建抛异常，已经创建的 joinable 线程也会先被收尾；正常路径也保证输出前全部 join。

## 验证：锁让结果确定

完整源码：[demos/18.cpp](../demos/18.cpp)

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/18.cpp -o build/demo_18
./build/demo_18
```

预期输出：

```text
counter: 20000
```

四条线程对 `counter` 的每次递增都先取得同一把锁，输出又发生在全部 join 之后，所以结果稳定。demo 每次循环都加锁是为了看清规则；实际计算常先得到线程局部结果，再用较短的临界区合并。

## 验证工具：ThreadSanitizer

ASan 和 UBSan 不负责检测普通数据竞争。可选实验 [thread_race_lab.cpp](../labs/thread_race_lab.cpp) 故意省略锁，只用于观察 ThreadSanitizer 报告：

```bash
c++ -std=c++17 -g -pthread -fsanitize=thread \
  labs/thread_race_lab.cpp -o build/thread_race_lab
./build/thread_race_lab
```

报告应指出两条线程对 `counter` 的冲突访问。ThreadSanitizer 不能和 AddressSanitizer 放在同一次构建中；当前编译器或平台不支持其运行时时，可以跳过这个实验，但语言规则不会因此改变。

## 局限与常见坑

- mutex 必须比所有使用它的线程活得久。
- 不要取出受保护数据的指针或引用，再在锁外访问它。
- 读取和写入必须遵守同一加锁协议。
- 不要持锁等待可能需要该锁才能完成的线程或 future。
- 两把锁的取得顺序不一致会导致死锁；优先简化所有权，确需多锁时使用 `std::scoped_lock`。
- 锁只保护临界区，不会延长被引用对象的生命周期。
- “没有崩溃”或“这次数字正确”都不能证明不存在数据竞争。
- ThreadSanitizer 只检查实际运行到的路径，不能替代代码审查和明确的不变量。

## 三级练习与完成标准

1. **预测：** 去掉锁后，为什么不能把结果仅描述为“可能小于 20000”？只分析，不运行错误版本。
2. **修改：** 每条线程先用局部变量累计 5000，最后只锁一次并合并到 `counter`。
3. **独立：** 设计 `ThreadSafeScores`，把 `vector` 和 mutex 封装在一起，提供 `add` 和返回副本的 `snapshot`；不要向调用者暴露内部容器的引用。

完成标准：能为一组共享状态写出统一加锁规则，使用 RAII 管理锁和线程，并能指出无锁读取、临界区过大、锁顺序相反和泄漏内部引用的位置。
