# 18 · 数据竞争与互斥锁

[返回学习地图](../README.md) · [下一篇：条件变量与生产者消费者](19-条件变量与生产者消费者.md)

## 本篇目标

理解数据竞争，使用 `std::mutex` 和 `std::lock_guard` 保护共享状态，并识别死锁与锁范围问题。

## 学习作用

两个线程并发访问同一内存位置，至少一个访问会写入，至少一个访问不是 atomic，并且二者没有同步，就会产生数据竞争和未定义行为。互斥锁让一组相关操作成为临界区，是实际项目里保护容器和业务不变量的基础工具。

## Java 对照

| Java | C++17 | 关键差别 |
| --- | --- | --- |
| `synchronized` | mutex + lock_guard | lock_guard 用 RAII 保证离开作用域自动解锁 |
| `ReentrantLock` + try/finally | mutex + lock_guard/unique_lock | `std::mutex` 不是可重入锁，重复锁同一把会出问题 |
| 并发集合 | 项目选定的并发容器或自行加锁 | vector/map 本身不自动变成线程安全 |
| `volatile` | 不能对应 C++ volatile | C++ volatile 不能修复数据竞争；简单原子值见第 21 篇 |

## 数据竞争不是“偶尔少算”

`++counter` 包含读取、加一、写回。两条线程无锁执行时可能互相覆盖，而且 C++ 把这种对同一内存位置的无同步冲突访问定义为未定义行为。编译器不需要保留你凭直觉想象的执行顺序。

“同一内存位置”比“同一个对象”更精确。同一 struct 中两个独立的普通成员通常位于不同内存位置，不会仅因属于同一对象就自动产生数据竞争；但多个成员若共同组成“余额与流水号必须一致”之类的业务不变量，仍应放在同一个锁协议中。对容器做 push、erase 等结构修改时，不要同时无锁读取或修改该容器。

同一共享状态的所有并发访问必须遵守同一套同步规则。只给写入加锁、读取不加锁，仍可能是数据竞争；把指针声明成 const 也不等于线程安全。

## 用 RAII 管锁

```cpp
{
    std::lock_guard<std::mutex> lock(mutex);
    ++counter;
} // lock 析构，mutex 自动解锁
```

不要手写 `mutex.lock()` 后经过多个 return/throw 再人工 unlock。lock_guard 即使因异常离开作用域也会解锁。锁住的范围要覆盖完整不变量，同时尽量不要包含耗时 I/O、sleep、未知回调、join 或 future.get。

同时获取两把互斥锁时，线程 A 按 m1→m2、线程 B 按 m2→m1，可能互相等待形成死锁。C++17 可使用 `std::scoped_lock lock(m1, m2)` 统一处理多把锁；更重要的是让项目保持清楚的锁顺序与所有权设计。

## 可运行 demo

源码：[demos/18.cpp](../demos/18.cpp)：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -pthread \
  demos/18.cpp -o build/demo_18
./build/demo_18
```

```cpp
#include <functional>
#include <iostream>
#include <mutex>
#include <thread>
#include <vector>

class JoiningThreads {
public:
    explicit JoiningThreads(std::vector<std::thread>& threads) : threads_(threads) {}
    ~JoiningThreads() {
        for (auto& thread : threads_) {
            if (thread.joinable()) thread.join();
        }
    }

    JoiningThreads(const JoiningThreads&) = delete;
    JoiningThreads& operator=(const JoiningThreads&) = delete;

private:
    std::vector<std::thread>& threads_;
};

void increment(int& counter, std::mutex& mutex, int times) {
    for (int index{0}; index < times; ++index) {
        std::lock_guard<std::mutex> lock(mutex);
        ++counter;
    }
}

int main() {
    int counter{0};
    std::mutex mutex;
    {
        std::vector<std::thread> workers;
        JoiningThreads joining{workers};
        for (int index{0}; index < 4; ++index) {
            workers.emplace_back(increment, std::ref(counter), std::ref(mutex),
                                 5000);
        }
    }
    std::cout << "counter: " << counter << '\n';
}
```

预期输出：

```text
counter: 20000
```

四条线程共享 counter 和 mutex，每次增加都先取得同一把锁。JoiningThreads 借用线程容器，并在析构时 join 每个仍可 join 的线程；即使循环中某次线程创建抛异常，已经创建的线程也会先被安全收尾。额外的大括号让 joining 在输出前析构，因此 main 只在全部 join 后读取 counter，结果确定。这里每次循环都锁一次是为了展示规则；高频计算通常让每条线程先算自己的局部结果，最后只锁一次合并，减少争用。

## 常见坑

- mutex 必须比所有使用它的线程活得久。
- 不要复制受锁保护的数据地址后绕开锁访问。
- 不要持有一把锁去等待需要同一把锁才能结束的线程或 future。
- ASan/UBSan 不检测数据竞争；ThreadSanitizer 是另一套工具，需单独构建，平台也未必支持。
- 没有崩溃、最终数字碰巧正确，都不能证明无竞争。

可选的 [thread_race_lab.cpp](../labs/thread_race_lab.cpp) 故意包含数据竞争，只用于观察 ThreadSanitizer 报告，不要把它当普通示例运行：

```bash
c++ -std=c++17 -g -pthread -fsanitize=thread \
  labs/thread_race_lab.cpp -o build/thread_race_lab
./build/thread_race_lab
```

报告应指向两条线程对 counter 的冲突访问。ThreadSanitizer 不能与 AddressSanitizer 混在同一次构建中；如果当前编译器/平台不支持其运行时，跳过这个可选 lab，仍按语言规则认定原代码错误。

## 三级练习与完成标准

1. 预测：去掉锁后为什么不能把“可能小于 20000”当作唯一结果？只分析，不运行错误版本。
2. 修改：每条线程用局部变量累计 5000，最后锁一次加到 counter。
3. 独立：设计一个 ThreadSafeScores 类，把 vector 与 mutex 封装在一起，提供 add 和返回副本的 snapshot；调用者不能拿到内部 vector 的引用。

完成标准：能给共享状态写出统一加锁规则，使用 RAII 锁，并指出代码中可能持锁过久、锁顺序相反或无锁读取的位置。
