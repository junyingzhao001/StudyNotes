# 01 · 编译运行与程序结构

[返回学习地图](../README.md) · [上一篇：C++ 心智模型](00-先建立C++心智模型.md) · [下一篇：作用域、头文件与宏定义](01A-作用域头文件与宏定义.md)

## 先说结论

C++ 源码不能直接当作程序运行：它要先经过预处理、编译和链接，生成本机可执行文件。遇到错误时，先判断失败发生在哪个阶段，比从整屏报错中猜原因更有效。

读完本篇，你能独立把 `demos/01.cpp` 构建成程序并运行，能指出 `main`、`#include`、`std::cout` 和返回码的作用，也能区分常见的编译错误与链接错误。这是进入任何 C++ 项目时的第一步。

## 问题：同一个“构建失败”可能来自不同阶段

C++ 构建主线是：

```text
.cpp 源码
   │ 预处理：展开 #include 和宏
   ▼
编译单元
   │ 编译：检查语法和类型，生成机器码片段
   ▼
.o 目标文件
   │ 链接：把目标文件和库中的实现组合起来
   ▼
可执行文件
   │ 运行
   ▼
输出与退出码
```

| 失败阶段 | 常见现象 | 首先检查 |
| --- | --- | --- |
| 预处理/编译 | 名字未声明、类型不匹配、缺分号 | 第一条指向自己源码的诊断 |
| 链接 | `undefined symbol` / `undefined reference` | 实现所在 cpp 或库是否参与链接 |
| 运行 | 输出错误、异常、崩溃、非零退出码 | 输入、业务状态和调用路径 |

把错误归到正确阶段，才能选择正确修复方向。

## 方案一：先看懂最小程序的四个角色

关键代码来自完整的 [demos/01.cpp](../demos/01.cpp)：

```cpp
int main() {
    const int days = 7; // 初始化后不再修改
    std::cout << "Hello, C++17!" << '\n';
    std::cout << "Plan: " << days << " days" << '\n';
    return 0;
}
```

- `#include <iostream>` 让当前编译单元看见标准输入输出相关声明。
- `main` 是程序入口。
- `std::cout` 是标准输出流；这里的 `<<` 表示依次写入内容。
- `'\n'` 写入换行。
- `return 0` 通常表示程序成功结束。
- `std::` 表示名字来自 C++ 标准库的 `std` 命名空间。

`const int days = 7` 创建并初始化一个不再通过该变量修改的整数。常见初始化写法和 const 会在第 02 篇继续说明。

## 方案二：用一条命令完成编译和链接

从课程根目录执行：

```bash
mkdir -p build
c++ -std=c++17 -Wall -Wextra -Wpedantic -g demos/01.cpp -o build/demo_01
```

这条命令的主要部分：

| 参数 | 作用 |
| --- | --- |
| `-std=c++17` | 按 C++17 标准构建 |
| `-Wall -Wextra -Wpedantic` | 开启常用警告 |
| `-g` | 保留调试信息 |
| `-o build/demo_01` | 指定生成的可执行文件 |

命令没有写 `-c`，所以编译器驱动会连续完成编译和链接。

如果想观察边界，可以拆成两步：

```bash
c++ -std=c++17 -Wall -Wextra -Wpedantic -g -c demos/01.cpp -o build/01.o
c++ build/01.o -o build/demo_01
```

第一条只生成目标文件，第二条才生成可执行文件。

## Java/Kotlin 对照

| Java/Kotlin 常见流程 | C++ 常见流程 |
| --- | --- |
| 源码编译成字节码，再由 JVM 执行 | 源码编译并链接成本机可执行文件 |
| `javac` 编译，`java` 启动 JVM | `c++` 编译器驱动可连续完成编译和链接 |
| import 让类型名可见，运行还依赖 classpath | include 让头文件内容可见，非内联实现通常还要由目标文件或库参与链接 |
| JVM 异常栈常用于定位运行错误 | C++ 还要先区分编译诊断、链接诊断和运行错误 |

`#include` 不是包管理器，也不保证某个非内联函数的实现已经链接进程序。模板和 inline 函数的定义常直接位于头文件中，因此更准确的判断是：调用处必须看见所需声明或定义，最终程序还必须获得所有需要链接的实现。

## 验证：运行并核对输出

```bash
./build/demo_01
```

预期输出：

```text
Hello, C++17!
Plan: 7 days
```

终端还可以检查退出码：

```bash
./build/demo_01
echo $?
```

正常情况下最后显示 `0`。

## 常见坑

- 只看报错最后一行。编译器常因前面的一个错误产生后续连锁诊断，应先看第一条与自己源码有关的错误。
- 认为 include 头文件就等于链接了实现。声明可见后，仍可能在链接阶段缺少目标文件或库。
- 把警告全部忽略。未使用变量、可疑转换和控制流问题经常先以警告出现。
- 在错误目录运行程序。`./build/demo_01` 是相对于当前工作目录的路径。
- 修改源码后直接运行旧可执行文件，却忘记重新构建。

## 三级练习

1. **预测**：把 days 改成 10，哪一行输出会变化？为什么第一行不变？
2. **修改**：增加一行输出自己的学习目标，重新构建后运行。
3. **独立完成**：先删除一个分号观察编译错误；恢复后只声明并调用一个未定义函数，观察链接错误。记录两类错误信息中最有用的一行。

## 完成标准

能用一步式或两步式命令生成并运行程序；能说出 main、include、std 和返回码的角色；看到 `undefined reference/symbol` 时会优先检查链接内容。
